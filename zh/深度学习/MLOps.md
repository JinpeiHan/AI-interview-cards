# ML 系统设计与 MLOps

## 生命周期与训练

Q1：***描述一个端到端的机器学习生命周期，MLOps 关注的是什么？***

- 典型阶段：
    1. **问题定义**：业务目标 → ML 目标 → 指标（离线指标与线上 KPI 的对应关系）、约束（延迟、成本、合规）
    2. **数据**：采集、标注、清洗、校验、特征工程、数据版本化
    3. **训练与实验**：基线 → 迭代、超参搜索、实验追踪
    4. **评估**：离线指标、切片分析（slice）、公平性、鲁棒性
    5. **部署**：打包、注册、灰度发布
    6. **监控与反馈**：数据/模型/业务监控，收集新标签 → 再训练
- MLOps 的核心：让以上循环**可复现、自动化、可观测、可回滚**；与 DevOps 不同之处在于 ML 系统同时依赖**代码、数据、模型**三类资产，且会在没有代码变更的情况下"静默退化"。
- 成熟度（参考 Google 的分级）：Level 0 手工脚本 → Level 1 训练流水线自动化 + 持续训练 → Level 2 流水线本身的 CI/CD。
- 名言式追问：Sculley et al. 2015 "Hidden Technical Debt in ML Systems"——模型代码只占系统很小一部分，胶水代码、管道丛林、配置债、反馈环才是主要风险。

Q2：***离线训练（批训练）和在线训练（增量/流式训练）有什么区别？如何选择？***

- **离线批训练**：周期性（天/周）在全量或滑窗数据上从头或热启动训练。
    - 优点：稳定、易复现、易评估和回滚；缺点：模型时效性差，无法快速响应分布变化
- **在线/增量训练**：在流式数据上持续更新（如 FTRL、流式 embedding 更新），分钟级甚至秒级生效。
    - 优点：时效性强，适合新闻、广告、短视频等快速变化场景、冷启动新 ID
    - 缺点：易受脏数据/攻击影响，**灾难性遗忘**，评估与回滚困难，系统复杂（需要样本拼接、实时特征）
- 常见折中：**天级全量训练 + 小时/分钟级增量更新**，加上自动校验门禁（指标异常则停止推送），并保留可回滚的快照。
- 选择依据：数据分布变化速度、新实体比例、对新鲜度的收益是否覆盖工程成本——可以通过"用 N 天前的模型 vs 最新模型"的离线回测量化**模型陈旧（staleness）**带来的损失。

## 特征与数据

Q3：***什么是特征存储（Feature Store）？它解决了什么问题？***

- 统一管理特征的**定义、计算、存储和服务**的系统（如 Feast、Tecton、各大厂自研）。
- 组成：
    - **离线存储**（数仓/数据湖，如 Hive、Parquet、BigQuery）：用于生成训练集，支持历史回溯
    - **在线存储**（低延迟 KV，如 Redis、Cassandra、DynamoDB）：用于线上推理，毫秒级读取最新值
    - **特征注册表**：特征元数据、负责人、血缘、版本
    - 批/流计算管道，写入两端（物化）
- 解决的问题：
    - **训练-服务不一致**（同一份特征定义驱动两端）
    - **特征复用**，避免各团队重复开发
    - **时点正确的 join**（point-in-time join）
    - 特征的发现、治理、监控

Q4：***什么是训练-服务偏差（training-serving skew）？有哪些来源？如何避免？***

- 定义：模型在训练和线上推理时看到的数据/处理逻辑不一致，导致离线指标好、线上效果差。
- 来源：
    - **代码路径不同**：离线用 Python/SQL 计算特征，线上用 Java/C++ 重写，细节不一致（缺失值处理、分桶边界、分词器版本）
    - **数据时效不同**：训练用 T+1 完整数据，线上只有部分实时数据
    - **特征穿越**：训练用到了预测时刻之后才可得的信息
    - **分布差异**：训练样本经过筛选/采样，线上是全量流量；或者模型自身影响了数据（反馈环）
    - 依赖版本、预处理参数（归一化均值方差）未随模型一起打包
- 避免：
    - 同一份特征代码/特征存储服务两端；预处理逻辑**打包进模型**（如 TF Transform、把 tokenizer 与模型一起版本化）
    - **线上特征日志回流（log-and-wait）**：把推理时实际使用的特征落盘，直接作为训练样本，从根本上消除偏差
    - 上线前做**一致性校验**：同一批请求离线计算 vs 线上计算的特征逐项对比、预测值对比
    - 监控线上特征分布与训练分布的差异

Q5：***什么是时点正确性（point-in-time correctness）？如何防止特征穿越/标签泄露？***

- 构造训练样本时，每个样本的特征必须是**事件发生时刻 $t$ 之前**实际可得的值，不能用 $t$ 之后更新的值。
- 例：预测用户 $t$ 时刻是否下单，如果使用了"用户最近 7 天下单数"的**当前**快照（包含 $t$ 之后的下单），就是穿越；离线 AUC 虚高，上线崩塌。
- 做法：
    - 特征按 (entity, timestamp) 存储历史版本，训练集生成时做 **as-of join**：取 $\max\{t_f : t_f\le t_{event}\}$ 的特征值
    - 考虑**特征可用延迟**：如果某特征 T+1 才产出，则 join 时要求 $t_f\le t_{event}-\text{delay}$
    - 按**时间切分**训练/验证/测试集，而不是随机切分
    - 检查"过于好"的特征（单特征 AUC 极高常是泄露信号）

```sql
-- as-of join 示意：为每个事件取事件时刻之前最新的特征值
SELECT e.user_id, e.event_ts, e.label, f.feat_value
FROM events e
LEFT JOIN LATERAL (
    SELECT feat_value FROM user_features f
    WHERE f.user_id = e.user_id AND f.feature_ts <= e.event_ts
    ORDER BY f.feature_ts DESC LIMIT 1
) f ON TRUE;
```

Q6：***如何做数据质量检查？***

- **模式（schema）校验**：字段、类型、取值范围、枚举值、非空约束。
- **统计校验**：缺失率、均值/分位数、基数（cardinality）、唯一性、与上一批次/训练集分布的差异。
- **业务规则**：如价格 > 0、点击 ≤ 曝光、时间戳不在未来。
- **量级校验**：数据行数突降/暴涨、上游延迟、分区缺失。
- **标签质量**：标注一致性（Cohen's kappa）、噪声标签检测、正负比例突变。
- 工具：Great Expectations、TFDV（TensorFlow Data Validation）、Deequ、Pandera、dbt tests。
- 放置位置：数据入湖时、特征管道产出时、训练前（**门禁**：校验失败则中止训练）、线上推理请求入口。
- 原则：数据问题是线上事故最常见的根因，校验要**自动化 + 告警 + 阻断**，而非只看报表。

## 部署与服务

Q7：***模型服务有哪些模式？各自适用于什么场景？***

| 模式 | 方式 | 延迟 | 适用场景 |
| --- | --- | --- | --- |
| **批量预测** | 定时任务对全量实体打分，结果写入 KV/表 | 小时/天级新鲜度，读取极快 | 用户画像、流失预测、离线推荐候选、营销名单 |
| **在线实时推理** | 请求触发，同步调用模型服务（REST/gRPC） | 毫秒级 | 搜索排序、风控决策、广告 CTR、对话 |
| **流式推理** | 消费事件流（Kafka/Flink），近实时打分 | 秒级 | 交易欺诈实时监测、IoT 异常检测、实时特征更新 |
| **端侧推理** | 模型部署到手机/边缘设备 | 无网络开销 | 隐私敏感、离线可用、超低延迟 |

- 常见混合：**批量预计算 + 在线轻量重排**（如召回离线生成、精排在线）。
- 服务化工具：TorchServe、Triton Inference Server、TF Serving、BentoML、KServe/Seldon（K8s）、vLLM/SGLang（LLM）。
- 设计考虑：吞吐 vs 延迟（动态 batching）、扩缩容、冷启动、多模型共享 GPU、降级策略（模型超时返回规则/缓存结果）。

Q8：***如何优化模型推理延迟？***

- **模型层面**：
    - **知识蒸馏**：大模型（teacher）软标签训练小模型（student），$\mathcal L=\alpha\,\mathrm{CE}(y,p_s)+(1-\alpha)T^2\,\mathrm{KL}(p_t^{T}\Vert p_s^{T})$
    - **量化**：FP32 → FP16/BF16 → INT8/INT4（PTQ 训练后量化、QAT 量化感知训练；LLM 常用 GPTQ、AWQ、FP8）
    - **剪枝**：结构化剪枝（通道/层/注意力头）才能获得真实加速
    - 更高效架构、减少特征数量、早退（early exit）
- **运行时/编译**：ONNX Runtime、TensorRT、`torch.compile`、算子融合、FlashAttention、KV cache（LLM）。
- **系统层面**：
    - **缓存**：结果缓存（热门请求）、特征缓存、embedding 缓存、LLM 的 prompt/prefix cache
    - **动态 batching**、并发控制、GPU 利用率优化
    - **级联架构**：召回 → 粗排 → 精排，越靠后模型越重、候选越少
    - 预计算（物品塔离线算好 + ANN 检索）、异步并行获取特征
- 指标要看 **P99 尾延迟**而非平均；先 profiling 定位瓶颈（往往是特征获取/网络 I/O 而不是模型计算）。

Q9：***模型注册表（Model Registry）和版本管理需要记录什么？***

- 模型注册表是模型的"制品仓库 + 状态机"（MLflow Model Registry、W&B Registry、SageMaker、Vertex AI 等）。
- 每个模型版本应记录：
    - 模型文件与**签名**（输入输出 schema）、依赖环境（Docker 镜像/conda 锁文件）
    - **血缘**：训练代码 commit、数据版本/快照、特征列表与版本、超参数、随机种子
    - 评估指标（总体 + 关键切片）、模型卡（用途、局限、公平性）
    - 状态：`Staging` → `Production` → `Archived`，以及审批人、上线时间
- 作用：可追溯（线上问题能回溯到哪份数据和代码）、**一键回滚**、审计合规、多版本并行（A/B）。
- 数据版本化工具：DVC、lakeFS、Delta Lake/Iceberg 的时间旅行。

Q10：***ML 中的 CI/CD/CT 分别是什么？和传统软件有何不同？***

- **CI（持续集成）**：除代码单测外，还要测试**数据**和**模型**：
    - 特征逻辑单测、数据 schema 校验、训练管道小样本冒烟测试（能跑通、loss 下降）
    - 模型质量测试：在固定评估集上不低于基线、关键切片不退化、推理延迟/内存不超标
- **CD（持续交付/部署）**：自动打包模型服务、部署到 staging、影子/金丝雀验证后推到生产；支持自动回滚。
- **CT（持续训练）**：ML 特有，由调度或触发器（新数据、漂移、指标下降）**自动重训**、自动评估、满足门禁后自动注册/推送。
- 与传统软件的差异：
    - 测试结果是**统计性的**（指标阈值），不是确定性的通过/失败
    - 需要验证数据，产物（模型）依赖数据而不仅是代码
    - 部署的是"训练流水线"而不只是一个模型
- 工具：Kubeflow Pipelines、Airflow、Argo、TFX、Metaflow、GitHub Actions + MLflow。

Q11：***影子部署、金丝雀发布和 A/B 测试有什么区别？***

- **影子部署（shadow / dark launch）**：新模型接收复制的线上流量并产出预测，但**不影响用户**；比较与旧模型的预测差异、延迟、错误率、特征一致性。适合高风险场景（风控、定价），缺点是无法衡量对用户行为的影响。
- **金丝雀发布（canary）**：把小比例（1%→5%→25%→100%）真实流量切给新模型，监控系统指标与护栏指标，异常则自动回滚。目标是**降低发布风险**，而非精确衡量效果。
- **A/B 测试**：随机分流用户到对照/实验组，在足够样本量和时长下用统计检验比较业务指标，目标是**因果地评估效果**。
    - 要点：确定分流单元（用户而非请求，避免同一用户体验不一致）、功效分析计算样本量、预先定义主指标和**护栏指标**、避免偷看（peeking）、注意新奇效应和网络效应（社交/双边市场需按区域或时间片随机）
    - 方差缩减：CUPED
- 其他：**交错实验（interleaving）**用于排序模型，灵敏度更高；**多臂老虎机**在探索中减少损失。
- 典型顺序：离线评估 → 影子 → 金丝雀 → A/B → 全量。

## 监控与再训练

Q12：***线上 ML 系统需要监控哪些内容？数据漂移和概念漂移有什么区别？***

- 监控分层：
    - **系统层**：QPS、延迟（P50/P99）、错误率、资源利用率
    - **数据层**：输入特征缺失率、分布变化、schema 变化、上游数据延迟
    - **模型层**：预测分布（均值、正例率）、置信度分布、有标签后的准确率/AUC/校准度
    - **业务层**：CTR、转化率、GMV、坏账率等
- 漂移类型（设输入 $X$、标签 $Y$）：
    - **数据漂移/协变量漂移**：$P(X)$ 变了，$P(Y|X)$ 不变（如新用户群体涌入）
    - **标签/先验漂移**：$P(Y)$ 变了（如欺诈率上升）
    - **概念漂移**：$P(Y|X)$ 变了，同样的输入对应的正确输出改变（如疫情后消费习惯变化、欺诈者改变手法）
- 数据漂移不一定导致性能下降（不重要的特征漂移无所谓）；概念漂移一定需要新标签才能确认，往往只能靠性能指标或代理指标发现。

Q13：***PSI 和 KS 如何计算？如何用于漂移检测？***

- **PSI（Population Stability Index）**：把特征（或模型分数）按基准分布分为 $B$ 个箱，基准占比 $e_i$，当前占比 $a_i$：
$$\mathrm{PSI}=\sum_{i=1}^{B}(a_i-e_i)\ln\frac{a_i}{e_i}$$
    - 是对称化的 KL 散度；经验阈值：$<0.1$ 稳定，$0.1\sim0.25$ 轻微变化需关注，$>0.25$ 显著漂移
    - 注意空箱需加平滑；分箱方式（等频）影响结果
- **KS 统计量**：两样本经验分布函数的最大差 $D=\sup_x|F_1(x)-F_2(x)|$，可做 KS 检验得 p 值；适用于连续变量。
    - 风控中 KS 也指**模型区分度**：好坏样本分数累积分布的最大差
- 其他：类别特征用卡方检验、JS 散度、Wasserstein 距离；高维/embedding 用 MMD、领域分类器（训练分类器区分新旧数据，AUC 越高漂移越大）。
- 实务：大样本下统计检验几乎总是"显著"，更应看**效应量**（PSI、距离）并结合特征重要性设定告警阈值。

```python
import numpy as np

def psi(expected, actual, bins=10, eps=1e-6):
    edges = np.unique(np.quantile(expected, np.linspace(0, 1, bins + 1)))
    edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(expected, edges)[0] / len(expected) + eps
    a = np.histogram(actual, edges)[0] / len(actual) + eps
    return float(np.sum((a - e) * np.log(a / e)))
```

Q14：***什么时候触发模型再训练？***

- **定时触发**：按天/周固定周期，简单可预测，适合分布平稳变化的场景。
- **数据量触发**：积累了足够多的新标注数据。
- **漂移触发**：输入或预测分布 PSI 超过阈值。
- **性能触发**：有标签后的线上指标低于阈值，或业务 KPI 下降。
- **事件触发**：上游数据/特征变更、业务规则改变、重大外部事件。
- 权衡：重训成本 vs 陈旧损失；用离线回测估计"模型随时间衰减曲线"来决定频率。
- 安全措施：重训后的模型必须经过与线上模型的**冠军/挑战者（champion/challenger）**比较、切片检查后才能推送；数据异常时触发重训可能反而有害（先查根因，脏数据要先修复）。

Q15：***标签延迟和反馈环会带来什么问题？如何处理？***

- **标签延迟**：真实标签要等很久才出现（贷款违约需数月、转化可能延迟几天）。
    - 问题：无法及时评估线上性能，训练样本中近期样本被误标为负（如转化未发生 ≠ 不会转化）
    - 处理：用**代理指标/早期信号**监控（点击、首期还款）；**延迟反馈建模**（如 DFM 对转化延迟建模、样本先入为负再纠正并做重要性加权）；设定标签成熟窗口；依靠漂移监控作为先行指标
- **反馈环**：模型的预测影响了后续训练数据。
    - 推荐系统：只有被推荐的物品才有曝光和点击 → **曝光偏差/流行度偏差**自我强化，"富者愈富"
    - 风控：被拒绝的申请永远没有违约标签 → **选择偏差**（需拒绝推断 reject inference）
    - 预测性警务等场景还会放大社会偏见
- 处理：保留少量**随机探索流量**（ε-greedy/bandit）、**逆倾向加权（IPS）**纠偏、记录曝光日志和打分时的倾向值、因果推断方法、对照组（holdout）长期保留。

## 实验与工程

Q16：***实验追踪需要记录什么？如何保证可复现性？***

- **实验追踪**（MLflow、Weights & Biases、Neptune、TensorBoard）记录：
    - 代码版本（git commit + 未提交 diff）、配置/超参数
    - 数据版本、特征列表、数据切分方式
    - 指标曲线、最终指标、切片指标，产物（模型、图表、预测文件）
    - 环境：库版本、硬件、随机种子
- **可复现性**要素：
    - **代码**：版本控制 + 配置文件化（Hydra 等），不要依赖 notebook 中的隐式状态
    - **数据**：不可变快照/版本（DVC、lakeFS、表格时间旅行），记录查询与时间点
    - **环境**：容器化、锁定依赖版本
    - **随机性**：固定 seed（Python/NumPy/PyTorch/CUDA），`torch.use_deterministic_algorithms(True)`；GPU 非确定性算子、分布式通信顺序仍可能导致微小差异
- 现实目标：**统计意义上可复现**（多种子结果的均值方差一致）往往比比特级一致更重要。

Q17：***ML 系统的成本如何管理？***

- **训练成本**：
    - 选择合适规模的模型，先用小规模实验和 scaling 曲线判断
    - 混合精度、梯度检查点、Spot/抢占式实例 + 断点续训
    - 增量训练替代全量重训、减少无效超参搜索（贝叶斯优化、早停的 Hyperband/ASHA）
- **推理成本**（长期往往远大于训练）：
    - 量化、蒸馏、批处理、GPU 共享（MIG、多模型同卡）、按流量**自动扩缩容**、Serverless 推理
    - 缓存、级联（便宜模型先过滤，困难样本才调用大模型）
    - LLM：模型路由（小模型处理简单请求）、prompt 压缩、prefix cache、限制输出长度
- **数据/存储成本**：特征生命周期管理、下线无用特征、冷热分层存储。
- **治理**：按团队/模型做成本归因与标签，设定预算告警；把"单次请求成本"作为与精度、延迟并列的上线指标。

## LLMOps

Q18：***LLMOps 与传统 MLOps 相比有哪些特殊之处？***

- 资产从"训练好的权重"变为 **prompt、检索数据、工具定义、模型供应商版本、微调适配器**等组合；很多团队不训练模型，而是编排模型。
- **Prompt 版本化**：prompt 当作代码管理（git / prompt registry），记录模板、变量、模型版本、温度等参数；任何改动都要经过评估再上线；注意上游模型版本升级也会造成行为变化，应锁定模型快照版本。
- **评估集（eval sets）**：
    - 构建覆盖核心场景、边界情况、历史失败案例的黄金集，持续从线上日志补充
    - 评估方式：精确匹配/程序化检查（JSON 格式、单元测试）、参考答案相似度、**LLM-as-a-judge**（需与人工标注校准，注意位置偏差、长度偏差、自我偏好）、人工评估
    - 作为 CI 的**回归测试**门禁
- **护栏（guardrails）**：输入侧（prompt 注入检测、PII 过滤、话题限制）、输出侧（有害内容、格式校验、事实性/引用校验、工具调用权限与参数校验），必要时人工审核。
- **追踪（tracing）**：记录每个请求的完整链路——prompt、检索结果、工具调用、中间步骤、token 用量、延迟、成本（LangSmith、Langfuse、Arize Phoenix、OpenTelemetry 的 GenAI 语义约定等），用于调试 Agent 多步失败和构建新评估样本。
- **监控**：token 成本、延迟（首 token 时间 TTFT）、拒答率、幻觉率、用户反馈（点赞/点踩）、检索命中率。
- **RAG 特有**：索引版本化、embedding 模型版本与索引一致、文档更新管道、检索质量评估（Recall@K、上下文相关性、忠实度）。

Q19：***LLM 应用上线后如何持续改进？***

- **数据飞轮**：线上 trace + 用户反馈 → 发现失败模式 → 聚类归因（检索没召回？prompt 不清？模型能力不足？）→ 加入评估集 → 修复 → 回归测试 → 发布。
- 改进手段按成本递增：prompt 优化 / few-shot → 改进检索（切块、重排、混合检索）→ 工具与流程设计 → 微调（SFT、LoRA、偏好优化 DPO）→ 换更强模型。
- 线上实验：对 prompt 或模型版本做 A/B，关注任务完成率、人工接管率、成本。
- 风险控制：模型供应商升级前用评估集回归；保留回退模型；对高风险动作（写操作、支付）加人工确认。

## 面试答题框架

Q20：***ML 系统设计面试应该如何作答？***

- 一个通用框架（建议主动掌控节奏，45 分钟内分配时间）：
    1. **澄清需求（~5 分钟）**：业务目标、用户规模、QPS、延迟预算、数据可得性、冷启动、合规约束；把业务目标翻译为 **ML 问题**（分类/排序/回归/生成）
    2. **指标**：离线指标（AUC、NDCG、Recall@K、校准度）+ 线上指标（CTR、留存、GMV）+ 护栏指标（延迟、投诉率），说明二者如何对齐
    3. **数据与标签**：数据来源、标签如何获得（显式/隐式反馈、人工标注）、正负样本定义、采样、标签延迟与偏差
    4. **特征工程**：用户/物品/上下文/交叉特征，实时 vs 批量特征，embedding
    5. **模型**：从简单基线（规则、LR、GBDT）出发，再到深度模型，说明权衡；大规模场景给出**多阶段架构**（召回 → 粗排 → 精排 → 重排）
    6. **训练**：损失函数、类别不平衡、训练频率、离线评估方法（按时间切分）
    7. **服务**：批量/在线、延迟优化、缓存、特征存储、降级
    8. **评估与上线**：影子 → 金丝雀 → A/B
    9. **监控与迭代**：漂移、再训练、反馈环、公平性与安全
- 加分点：主动讨论**权衡**（精度 vs 延迟 vs 成本）、量化估算（QPS × 候选数 → 计算量）、失败模式与兜底方案、先给出端到端方案再深入某个模块。
- 常见失分：一上来就选模型、忽略数据和标签来源、不提指标和监控、只讲离线不讲线上。

Q21：***以"设计一个欺诈交易检测系统"为例，简要说明关键设计点***

- **需求**：实时拦截（延迟预算如 < 100ms）、极度不平衡（欺诈率常远低于 1%）、误拦成本（用户体验）vs 漏拦成本（资金损失）。
- **指标**：PR-AUC、固定误报率下的召回、拦截金额；线上看欺诈损失率、误拦投诉率。
- **数据与标签**：拒付/人工审核结果作为标签，**标签延迟**数周；被拦截交易无真实标签（选择偏差），需保留小比例放行或人工复核样本。
- **特征**：实时窗口统计（过去 1 分钟/1 小时交易次数、金额）、设备/IP/地理一致性、商户风险、图特征（共享设备的账户数、团伙关联）；用流计算（Flink）+ 在线特征存储，保证时点正确。
- **模型**：规则引擎兜底 + GBDT（强基线、可解释）+ 可选 GNN/序列模型；分数 → 决策阈值（放行/验证/拦截）按成本矩阵设定。
- **服务**：在线同步打分，特征获取并行化，超时降级到规则。
- **上线与监控**：影子运行对比规则系统 → 金丝雀；监控分数分布 PSI、拦截率突变、对抗性漂移（欺诈者适应新模型），高频再训练。

Q22：***常见的 MLOps 工具栈有哪些？如何选型？***

- **编排**：Airflow、Kubeflow Pipelines、Argo Workflows、Dagster、Prefect、Metaflow。
- **数据/特征**：Spark、Flink、dbt；Feast、Tecton；DVC、lakeFS、Delta Lake/Iceberg。
- **实验与注册**：MLflow、Weights & Biases、Neptune。
- **训练**：Ray（Train/Tune）、PyTorch DDP/FSDP、DeepSpeed、云平台（SageMaker、Vertex AI、Azure ML）。
- **服务**：Triton、TorchServe、BentoML、KServe、Ray Serve；LLM 用 vLLM、SGLang、TensorRT-LLM。
- **监控**：Prometheus + Grafana（系统）、Evidently、WhyLabs、Arize、NannyML（数据/模型）；LLM 用 Langfuse、LangSmith、Phoenix。
- 选型原则：团队规模与成熟度（小团队优先托管服务和少量工具）、与现有基础设施（K8s、云厂商）集成、避免过度工程——先解决可复现、监控和回滚这三个最痛的问题。
