# ML 系统设计与 MLOps

## 生命周期与训练

Q1：***描述一个端到端的机器学习生命周期，MLOps 关注的是什么？***

- **一个 ML 项目大致经历：问题定义 → 数据 → 训练实验 → 评估 → 部署 → 监控与反馈，然后用新数据再训练，形成闭环。MLOps 关注的是让这个循环可复现、自动化、可观测、可回滚。**
- 问题定义要把业务目标翻译成 ML 目标和指标，并明确延迟、成本、合规等约束。
- 和 DevOps 的区别：ML 系统同时依赖代码、数据、模型三类资产，而且可能在代码没变的情况下"静默退化"。
- 成熟度（Google 分级）：Level 0 手工脚本 → Level 1 训练流水线自动化 + 持续训练 → Level 2 流水线本身也有 CI/CD。
- 常被引用的观点（"Hidden Technical Debt in ML Systems"）：模型代码只占很小一部分，胶水代码、管道、配置和反馈环才是主要风险。

Q2：***离线训练（批训练）和在线训练（增量/流式训练）有什么区别？如何选择？***

- **离线训练按天或周在一批数据上周期性重训，稳定、易复现、易回滚，但跟不上分布变化；在线训练在数据流上持续更新，分钟级生效、时效性强，但容易被脏数据带偏、难评估难回滚，系统也更复杂。**
- 在线训练适合新闻、广告、短视频等变化快、新 ID 多的场景；缺点还包括灾难性遗忘。
- 常见折中：天级全量训练 + 小时/分钟级增量更新，配上自动校验门禁（指标异常就停止推送）和可回滚快照。
- 选择依据：分布变化有多快、新实体有多少，以及新鲜度带来的收益是否值得工程成本；可以离线回测"N 天前的模型 vs 最新模型"来量化模型陈旧的损失。

## 特征与数据

Q3：***什么是特征存储（Feature Store）？它解决了什么问题？***

- **特征存储是统一管理特征的定义、计算、存储和线上服务的系统（如 Feast、Tecton）。它最主要解决训练和线上用的特征不一致的问题，同时让特征可以复用，并保证构造训练集时时点正确。**
- 离线存储（数仓/数据湖）：生成训练集，支持历史回溯。
- 在线存储（Redis 等低延迟 KV）：线上推理时毫秒级读取最新特征值。
- 特征注册表：记录元数据、负责人、血缘和版本，方便发现和治理；由批/流管道把同一份定义同时写入两端。

Q4：***什么是训练-服务偏差（training-serving skew）？有哪些来源？如何避免？***

- **训练-服务偏差是指模型训练时和线上推理时看到的数据或处理逻辑不一致，导致离线指标好、线上效果差。最根本的解法是两端用同一份特征逻辑，或者直接把线上实际用到的特征记录下来当训练样本。**
- 常见来源：离线和线上是两套代码（缺失值、分桶、分词器版本不一致）；数据时效不同；特征穿越；训练样本经过筛选而线上是全量；预处理参数没和模型一起打包。
- 预防：用特征存储服务两端，把预处理逻辑打包进模型（如 tokenizer 与模型一起版本化）。
- 线上特征日志回流（log-and-wait）：把推理时实际使用的特征落盘，直接用于训练，从根上消除偏差。
- 上线前对同一批请求比较离线和线上算出的特征与预测；上线后持续监控两边分布差异。

Q5：***什么是时点正确性（point-in-time correctness）？如何防止特征穿越/标签泄露？***

- **时点正确性要求每个训练样本只使用在事件发生那一刻之前真正能拿到的特征值。如果用了事件之后才更新的值，就是特征穿越，离线 AUC 会虚高、上线就崩。**
- 例子：预测用户某时刻是否下单，却用了包含之后下单记录的"最近 7 天下单数"当前快照。
- 做法：特征按 (实体, 时间戳) 保存历史版本，构造训练集时做 as-of join，取事件时刻之前最新的那个值。
- 还要考虑特征产出延迟：T+1 才产出的特征，join 时要把时间再往前推。
- 按时间切分训练/验证/测试集；对单特征效果"好得离谱"的特征保持警惕，它常是泄露信号。

Q6：***如何做数据质量检查？***

- **数据质量检查要覆盖 schema、统计分布、业务规则、数据量和标签质量几个方面，并在数据入库、特征产出、训练前和线上入口设置自动化校验，失败就告警甚至阻断，而不是只看报表。**
- schema 与业务规则：字段、类型、取值范围、非空；如价格 > 0、点击 ≤ 曝光、时间戳不在未来。
- 统计与量级：缺失率、分位数、基数、与上一批或训练集的分布差异；行数突变、上游延迟、分区缺失。
- 标签质量：标注一致性、噪声标签、正负比例突变。
- 工具：Great Expectations、TFDV、Deequ、Pandera、dbt tests；数据问题是线上事故最常见的根因。

## 部署与服务

Q7：***模型服务有哪些模式？各自适用于什么场景？***

- **主要有四种：批量预测（定时离线打分，适合用户画像、营销名单）、在线实时推理（请求触发，毫秒级，适合搜索排序、风控、广告）、流式推理（消费事件流，秒级，适合实时欺诈监测）和端侧推理（部署在设备上，适合隐私敏感和离线场景）。实际系统常常混用。**

| 模式 | 新鲜度/延迟 | 典型场景 |
| --- | --- | --- |
| 批量预测 | 小时/天级，读取极快 | 用户画像、流失预测、离线推荐候选 |
| 在线实时推理 | 毫秒级 | 搜索排序、风控决策、广告 CTR |
| 流式推理 | 秒级 | 交易欺诈监测、IoT 异常检测 |
| 端侧推理 | 无网络开销 | 隐私敏感、离线可用 |

- 常见混合：召回离线批量生成，精排在线计算。
- 工具：Triton、TorchServe、TF Serving、BentoML、KServe；LLM 用 vLLM、SGLang。
- 设计要点：吞吐与延迟（动态 batching）、扩缩容、多模型共享 GPU、超时降级到规则或缓存结果。

Q8：***如何优化模型推理延迟？***

- **先 profiling 找瓶颈，再从三层入手：模型层把模型变小变快（蒸馏、量化、剪枝），运行时层用编译和算子优化，系统层用缓存、批处理、级联和预计算。指标要看 P99 尾延迟，而且瓶颈往往在特征获取和网络 I/O 而不是模型计算。**
- 模型层：知识蒸馏；量化到 FP16/INT8/INT4（训练后量化或量化感知训练）；结构化剪枝才有真实加速；早退。
- 运行时：ONNX Runtime、TensorRT、`torch.compile`、算子融合、FlashAttention、LLM 的 KV cache。
- 系统层：结果/特征/embedding 缓存、动态 batching、召回 → 粗排 → 精排的级联、物品向量离线预计算 + ANN 检索、并行获取特征。

Q9：***模型注册表（Model Registry）和版本管理需要记录什么？***

- **模型注册表是模型的"制品仓库 + 状态机"。每个版本要记录模型文件和输入输出签名、运行环境、完整血缘（代码、数据、特征、超参、种子）、评估结果和所处状态，这样线上出问题能追溯，也能一键回滚。**
- 血缘：训练代码 commit、数据快照、特征列表和版本、超参数、随机种子。
- 评估：总体和关键切片指标，以及模型卡（用途、局限、公平性）。
- 状态流转：Staging → Production → Archived，附审批人和上线时间；支持审计和多版本 A/B。
- 工具：MLflow、W&B、SageMaker、Vertex AI；数据版本化用 DVC、lakeFS、Delta Lake/Iceberg 时间旅行。

Q10：***ML 中的 CI/CD/CT 分别是什么？和传统软件有何不同？***

- **CI 除了测代码，还要测数据和模型；CD 自动打包部署模型服务并支持回滚；CT（持续训练）是 ML 特有的，在新数据、漂移或指标下降时自动重训、评估，通过门禁后自动上线。和传统软件最大的不同是：测试结果是统计性的阈值判断，交付物依赖数据，部署的是整条训练流水线。**
- CI：特征逻辑单测、schema 校验、小样本冒烟训练（能跑通、loss 下降），模型不低于基线、关键切片不退化、延迟和内存不超标。
- CD：部署到 staging，经影子或金丝雀验证再推到生产，异常自动回滚。
- 工具：Kubeflow Pipelines、Airflow、Argo、TFX、Metaflow、GitHub Actions + MLflow。

Q11：***影子部署、金丝雀发布和 A/B 测试有什么区别？***

- **三者目的不同：影子部署让新模型跑线上流量但不影响用户，用来验证正确性和性能；金丝雀发布把一小部分真实流量逐步切给新模型，用来降低发布风险；A/B 测试随机分流并做统计检验，用来因果地衡量对业务指标的效果。**
- 影子部署适合风控、定价等高风险场景，但测不出对用户行为的影响。
- 金丝雀按 1% → 5% → 25% → 100% 推进，监控护栏指标，异常自动回滚。
- A/B 要点：按用户分流、事先算样本量、预定义主指标和护栏指标、不要中途偷看、注意新奇效应和网络效应；可用 CUPED 降方差。
- 排序模型还可用交错实验（更灵敏）；典型顺序：离线评估 → 影子 → 金丝雀 → A/B → 全量。

## 监控与再训练

Q12：***线上 ML 系统需要监控哪些内容？数据漂移和概念漂移有什么区别？***

- **监控要分四层：系统（延迟、错误率）、数据（特征缺失和分布）、模型（预测分布、有标签后的效果）和业务（CTR、转化等）。数据漂移是输入分布变了而输入到输出的关系没变；概念漂移是同样的输入对应的正确答案变了。**
- 数据漂移例子：大量新用户群体涌入；它不一定伤害效果，不重要的特征漂移可以忽略。
- 标签漂移：标签本身的比例变了，比如欺诈率上升。
- 概念漂移例子：疫情后消费习惯改变、欺诈者换了手法；必须有新标签才能确认，通常靠效果指标或代理指标发现。

Q13：***PSI 和 KS 如何计算？如何用于漂移检测？***

- **PSI 把特征或模型分数按基准分布分箱，比较基准和当前每个箱的占比差异，是一种对称化的 KL 散度；KS 是两个样本经验累积分布之间的最大差距。两者都用来量化"现在的分布和基准差多少"，超过阈值就告警。**
- PSI 经验阈值：< 0.1 稳定，0.1–0.25 需关注，> 0.25 显著漂移；空箱要加平滑，常用等频分箱。
- KS 适合连续变量，可以给出 p 值；风控里 KS 也指模型区分好坏样本的能力。
- 其他方法：类别特征用卡方或 JS 散度，还有 Wasserstein 距离；高维 embedding 用 MMD 或训练分类器区分新旧数据（AUC 越高漂移越大）。
- 大样本下统计检验几乎总是"显著"，更应看效应量，并结合特征重要性设定阈值。
- 核心公式：$\mathrm{PSI}=\sum_{i}(a_i-e_i)\ln\frac{a_i}{e_i}$（$e_i$、$a_i$ 为基准与当前分布在第 $i$ 箱的占比）

Q14：***什么时候触发模型再训练？***

- **常见触发方式有：定时、积累到足够新标签、检测到漂移、线上效果下降，以及上游数据或业务规则变化等事件。频率要在重训成本和模型陈旧损失之间权衡，可以用离线回测画出模型随时间衰减的曲线来决定。**
- 定时触发简单可预测，适合分布平稳变化的场景。
- 漂移触发（如 PSI 超阈值）和性能触发（指标或 KPI 下降）更有针对性。
- 安全措施：新模型要和线上模型做冠军/挑战者对比和切片检查后才推送。
- 如果是数据异常引起的漂移，先查根因、修复脏数据，盲目重训反而有害。

Q15：***标签延迟和反馈环会带来什么问题？如何处理？***

- **标签延迟是指真实标签要很久才出现（如贷款违约要几个月），导致无法及时评估效果，近期样本还会被误当成负样本；反馈环是指模型的决策影响了后续训练数据，让偏差自我强化。前者靠代理指标和延迟反馈建模，后者靠保留探索流量和纠偏加权。**
- 标签延迟处理：用早期信号（点击、首期还款）监控；对转化延迟建模并做纠正和重要性加权；设定标签成熟窗口；以漂移监控作为先行指标。
- 反馈环例子：推荐系统只有被推荐的物品才有点击，造成"富者愈富"的曝光偏差；风控中被拒绝的申请永远没有违约标签，形成选择偏差（需要拒绝推断）。
- 反馈环处理：保留少量随机探索流量（ε-greedy/bandit）、逆倾向加权（IPS）、记录曝光和打分倾向、长期保留对照组。

## 实验与工程

Q16：***实验追踪需要记录什么？如何保证可复现性？***

- **实验追踪要记录代码版本、配置和超参数、数据版本和切分方式、各类指标与产物，以及运行环境和随机种子。可复现性靠四件事：代码版本化、数据快照、环境容器化、固定随机性。**
- 工具：MLflow、Weights & Biases、Neptune、TensorBoard。
- 代码：git commit + 配置文件化（如 Hydra），不要依赖 notebook 的隐式状态；数据：不可变快照（DVC、lakeFS、时间旅行）。
- 随机性：固定 Python/NumPy/PyTorch/CUDA 的种子并开启确定性算法；GPU 非确定性算子和分布式通信仍可能带来微小差异。
- 现实目标：多种子结果的均值和方差一致（统计意义上可复现）往往比逐比特一致更重要。

Q17：***ML 系统的成本如何管理？***

- **成本分训练、推理和数据存储三块，其中长期来看推理通常最贵。思路是：训练上用合适规模的模型和便宜的算力，推理上让模型更小、多批处理、多缓存、先用便宜模型过滤，并且按团队和模型做成本归因，把单次请求成本当作和精度、延迟并列的上线指标。**
- 训练：先做小规模实验看 scaling 趋势；混合精度、梯度检查点、抢占式实例 + 断点续训；增量训练、早停式超参搜索（Hyperband/ASHA）。
- 推理：量化、蒸馏、批处理、GPU 共享、自动扩缩容、级联；LLM 还可做模型路由、prompt 压缩、prefix cache、限制输出长度。
- 数据：下线无用特征、冷热分层存储；治理上设预算告警。

## LLMOps

Q18：***LLMOps 与传统 MLOps 相比有哪些特殊之处？***

- **LLMOps 管理的资产不再主要是自己训练的权重，而是 prompt、检索数据、工具定义、模型供应商版本和微调适配器的组合，很多团队是在编排模型而不是训练模型。因此重点变成：prompt 版本化、评估集做回归测试、输入输出护栏、全链路追踪和成本/质量监控。**
- prompt 当代码管理，连同模型版本和参数一起记录，改动先评估再上线；锁定模型快照，因为供应商升级也会改变行为。
- 评估集：覆盖核心场景、边界情况和历史失败案例，持续从线上补充；可用程序化检查、参考答案对比、LLM-as-a-judge（需与人工校准，注意位置和长度偏差）和人工评估。
- 护栏：输入侧防 prompt 注入、过滤 PII；输出侧检查有害内容、格式、事实性，以及工具调用的权限和参数。
- 追踪与监控：记录 prompt、检索结果、工具调用、token 和延迟（如 TTFT）；RAG 还要做索引和 embedding 模型版本管理，评估检索质量和忠实度。

Q19：***LLM 应用上线后如何持续改进？***

- **靠数据飞轮：从线上 trace 和用户反馈中发现失败案例，归因（检索没召回、prompt 不清、还是模型能力不够），加入评估集，修复后跑回归测试再发布。修复手段按成本从低到高尝试。**
- 改进顺序：prompt 优化 / few-shot → 改进检索（切块、重排、混合检索）→ 工具与流程设计 → 微调（SFT、LoRA、DPO）→ 换更强的模型。
- 线上对 prompt 或模型版本做 A/B，关注任务完成率、人工接管率和成本。
- 风险控制：供应商升级前先跑回归；保留回退模型；高风险动作（写操作、支付）加人工确认。

## 面试答题框架

Q20：***ML 系统设计面试应该如何作答？***

- **按固定框架主动掌控节奏：先澄清需求并把业务目标翻译成 ML 问题，再依次讲指标、数据与标签、特征、模型、训练、服务、上线评估和监控迭代。先给出端到端方案，再深入某个模块，并始终讨论精度、延迟、成本之间的权衡。**
- 澄清（约 5 分钟）：业务目标、规模和 QPS、延迟预算、数据可得性、冷启动和合规。
- 指标：离线指标（AUC、NDCG、校准）、线上指标（CTR、留存）和护栏指标，并说明如何对齐。
- 模型：从规则、LR、GBDT 等基线出发再到深度模型；大规模场景用召回 → 粗排 → 精排 → 重排的多阶段架构。
- 加分点：量化估算（QPS × 候选数）、失败模式与兜底方案；常见失分：一上来就选模型、不谈数据和标签、不提指标和监控、只讲离线。

Q21：***以"设计一个欺诈交易检测系统"为例，简要说明关键设计点***

- **这是一个实时、极度不平衡、误拦和漏拦成本都很高的问题。核心设计是：用实时窗口统计和图特征，在规则引擎兜底下用 GBDT 在线打分，按成本矩阵设阈值决定放行、验证还是拦截；同时处理标签延迟和选择偏差，并持续监控对抗性漂移。**
- 指标：PR-AUC、固定误报率下的召回、拦截金额；线上看欺诈损失率和误拦投诉率。
- 标签：拒付和人工审核结果，延迟数周；被拦截的交易没有真实标签，需保留少量放行或人工复核样本。
- 特征：过去 1 分钟/1 小时的交易次数和金额、设备/IP/地理一致性、商户风险、共享设备等图特征；用 Flink + 在线特征存储，保证时点正确。
- 服务与上线：延迟预算如 < 100ms，特征并行获取，超时降级到规则；先影子对比规则系统再金丝雀，监控分数 PSI 和拦截率突变，高频再训练。

Q22：***常见的 MLOps 工具栈有哪些？如何选型？***

- **工具栈按环节分：编排、数据与特征、实验与注册、训练、服务和监控，每个环节都有几种主流选择。选型看团队规模和现有基础设施，避免过度工程，先解决可复现、监控和回滚这三个最痛的问题。**
- 编排：Airflow、Kubeflow Pipelines、Argo、Dagster、Prefect、Metaflow；数据/特征：Spark、Flink、dbt、Feast、Tecton、DVC、lakeFS、Delta Lake/Iceberg。
- 实验与注册：MLflow、W&B、Neptune；训练：Ray、PyTorch DDP/FSDP、DeepSpeed、云平台（SageMaker、Vertex AI、Azure ML）。
- 服务：Triton、TorchServe、BentoML、KServe、Ray Serve；LLM 用 vLLM、SGLang、TensorRT-LLM。
- 监控：Prometheus + Grafana（系统）、Evidently、WhyLabs、Arize、NannyML（数据/模型）；LLM 用 Langfuse、LangSmith、Phoenix。小团队优先托管服务。
