# 工具调用

Q1：***什么是Function Calling / Tool Calling？它是如何工作的？***

- **Tool Calling是让LLM以结构化格式（通常是JSON）请求调用外部函数的能力：模型只输出"调用意图"，真正执行由应用负责。**
- 开发者提供工具定义（名称、描述、参数的JSON Schema）。
- 模型需要时输出工具名和参数；应用执行函数，把结果作为工具结果消息回传。
- 模型基于结果继续推理，可能再调用工具或给出最终回答；执行、权限、安全都在应用侧。

Q2：***模型是如何学会调用工具的？***

- **主要靠后训练：先在含工具定义、调用和结果的对话数据上做SFT，再用强化学习在真实或模拟环境里优化多步工具使用。**
- 推理时工具定义被注入到系统提示/特殊模板中，模型输出带特殊标记的调用，服务端解析成API里的tool call对象。
- 部分API支持受约束解码，保证参数严格符合JSON Schema。

Q3：***一个好的工具Schema应该如何设计？***

- **名称清晰、描述写清"什么时候用/不用"、参数类型明确，并围绕用户任务而不是底层API端点来设计。**
- 名称：动词开头、带命名空间，如`github_create_issue`。
- 参数：用明确类型、`enum`、`required`，参数名自解释（`user_id`而非`id`），别让模型做复杂格式转换。
- 粒度：高频组合操作可合并成一个工具。
- 返回值：精简、高信号（返回名称而非内部UUID），支持分页、过滤和截断。

Q4：***什么是MCP（Model Context Protocol）？解决了什么问题？***

- **MCP是Anthropic在2024年底提出的开放协议，标准化LLM应用与外部工具、数据源的连接，常被比作"AI应用的USB-C"。**
- 没有标准时，M个应用接N个工具需要M×N个定制集成；有了MCP，每个应用实现一次客户端、每个工具实现一次服务端，只需M+N。
- 目前已被主流模型厂商、IDE和Agent框架广泛支持。

Q5：***MCP的架构和核心概念是什么？***

- **MCP是Host-Client-Server架构：Host是AI应用，内部每个Client与一个Server一对一连接，Server暴露工具和数据。**
- 通信基于JSON-RPC 2.0，传输有本地stdio和远程Streamable HTTP（远程通常配OAuth）。
- Server提供三种原语：Tools（模型控制的函数）、Resources（应用控制的数据）、Prompts（用户控制的提示模板）。
- Client也提供能力：Sampling（Server借用Host的模型生成）、Elicitation（向用户要补充信息）、Roots（告知可访问范围）。

Q6：***MCP和普通Function Calling有什么关系？***

- **二者互补：Function Calling是模型层面"如何输出工具调用"的能力，MCP是应用层面"工具如何被发现、描述、调用和传输"的协议。**
- 运行时Host通过`tools/list`拿到Server的工具，转成模型API的工具定义。
- 模型发出tool call后，Host再通过`tools/call`转发给Server执行。

Q7：***使用MCP有哪些安全风险？***

- **主要风险是第三方Server和工具返回内容都可能操纵模型，加上Server往往持有高权限凭证。**
- 工具投毒：恶意Server在工具描述里藏指令；提示注入：工具返回的网页、邮件里含恶意指令。
- 权限过大被诱导执行破坏性操作；rug pull：Server在用户批准后偷改工具定义。
- 数据外泄：读私有数据的工具 + 能对外发送的工具组合使用。
- 防护：只用可信Server、最小权限、敏感操作人工确认、工具定义变更要提醒。

Q8：***什么是Structured Output（结构化输出）？有哪些实现方式？***

- **让模型输出严格符合预定义格式（通常是JSON Schema）的结果，最可靠的方式是解码时约束，保证一定符合Schema。**
- 提示约束：给格式和示例，最简单但不保证正确；JSON mode：保证是合法JSON但不保证符合Schema。
- Schema约束解码（strict mode）：解码时屏蔽不合法token，保证符合Schema。
- 借用工具调用（定义"提交结果"工具），或后处理用Pydantic校验、失败后把错误反馈给模型重试。
- 强约束可能略微影响推理质量，可以让模型先推理再输出结构化结果。

Q9：***工具调用出错时应该如何处理？***

- **按错误类型分别处理，把错误作为工具结果返回给模型而不是让运行时崩溃。**
- 参数错误：返回清晰可操作的错误信息（如"date必须是YYYY-MM-DD"），让模型自行修正。
- 临时错误（超时、限流、5xx）：运行时做指数退避重试，不必让模型感知。
- 永久错误（无权限、资源不存在）：明确告知模型，让它换方案或求助用户。
- 限制最大重试次数；有副作用的操作重试时保证幂等，避免重复下单或发邮件。

Q10：***什么是并行工具调用（Parallel Tool Calls）？有什么注意事项？***

- **模型在一次回复里输出多个相互独立的工具调用，运行时并发执行后一起返回，减少往返和延迟。**
- 典型场景：同时查多个城市天气、读多个文件、发多个搜索。
- 只有互不依赖的调用才能并行，每个结果要用`tool_call_id`对应回调用。
- 有副作用的写操作并行要考虑竞态，必要时在API中关闭并行调用。

Q11：***当工具数量非常多（几十到上千个）时，如何让模型正确选择工具？***

- **核心是不要把所有工具定义都塞进上下文，而是按任务动态检索、加载相关工具。**
- 工具检索/动态加载：用向量或关键词检索选出相关工具，或提供"搜索工具"的元工具按需加载。
- 分层路由：先选类别或子Agent，再在类别内选工具。
- 合并重叠工具、删除少用工具，用命名空间前缀区分服务（`slack_`、`jira_`）。
- 也可让Agent写代码调用API替代逐个工具定义，并用评估集持续测选择准确率。

Q12：***`tool_choice`参数有什么作用？***

- **它控制模型是否以及如何使用工具：auto（模型自己决定，默认）、required/any（必须调用至少一个）、指定工具（强制调用某个，常用于结构化抽取）、none（禁止调用）。**
- 部分支持扩展思考的模型中，强制调用工具可能与思考模式不兼容，要查具体API文档。

Q13：***工具返回的结果太长怎么办？***

- **在工具层就截断、分页、过滤，并告诉模型结果被截断以及如何获取更多。**
- 提供详细程度参数（`concise`/`detailed`）让模型按需选择。
- 大结果写入文件，只返回摘要和路径，模型按需读取；或用小模型先摘要。
- 清理历史中不再需要的旧工具结果。

Q14：***如何评估和改进工具的设计？***

- **用贴近真实使用的任务做评估，读完整轨迹找出模型误解工具的地方，再改描述、参数和返回格式迭代对比。**
- 指标：任务成功率、工具调用次数、错误率、token消耗。
- 常见问题：选错工具、参数错误、多余调用。
- 也可以让模型分析失败轨迹，建议如何改工具描述。

Q15：***工具调用中的“人工确认（human approval）”应如何设计？***

- **按风险分级：只读操作自动执行，不可逆或高影响操作（删除、转账、发邮件、部署）需要用户确认。**
- 确认界面展示具体参数和影响，而不是笼统的"是否允许"。
- 支持"本次允许/始终允许"等策略，平衡安全和体验。
- 被拒绝时把原因作为工具结果返回，让模型调整方案。

Q16：***Tool Calling和Code Execution（让模型写代码执行）各有什么优缺点？***

- **Tool Calling接口明确、易做权限和校验、更安全；Code Execution表达力强，中间数据留在执行环境里更省token，但需要沙箱且难审计。**
- Tool Calling的缺点：每次调用一次模型往返，复杂数据处理要多次调用，中间结果都经过上下文。
- Code Execution能在一段代码里组合多次调用、循环和过滤。
- 实践中结合使用：常规操作用工具，复杂数据处理交给代码执行。
