# Agent系统设计

Q1：***回答Agent系统设计题的一般框架是什么？***

- **先明确需求并判断是否真的需要Agent，再依次讲核心架构、可靠性与安全、性能与成本、评估与可观测性。**
- 需求：用户是谁、任务是什么、成功标准、规模、延迟成本要求、风险等级。
- 能用Workflow解决的部分尽量用Workflow。
- 架构讲模型、工具与数据源、上下文与记忆、单Agent还是多Agent；安全讲护栏、权限、沙箱、人在回路和降级。
- 性能讲缓存、流式、路由、并行；最后讲离线评估、线上监控和反馈闭环。

Q2：***设计一个电商客服Agent***

- **先用分诊路由：简单FAQ走RAG直接回答，复杂事务交给带工具的Agent（或按领域交接给专业Agent）；工具只能访问当前已验证用户的数据，高风险操作要人工审批。**
- 工具：`get_order`、`track_shipment`、`create_return`、`issue_refund`、`search_kb`、`escalate_to_human`；政策和FAQ用RAG保证基于最新政策。
- 护栏：退款超阈值或不合政策需审批；检测越狱注入，检查输出承诺是否超出政策。
- 用户情绪激动、多次未解决或主动要求时转人工，并附对话摘要。
- 评估：模拟用户（类似τ-bench）加真实工单回放，看解决率、政策遵守率、转人工率、满意度和多次运行一致性。

Q3：***设计一个代码Agent（Coding Agent）***

- **核心是一组精简工具（读文件、搜索、编辑、执行shell、版本控制）加上"改代码 → 跑测试 → 根据失败迭代"的验证闭环，并在沙箱中运行。**
- 上下文：不把整个仓库塞进去，而是按需搜索探索；启动时加载项目说明文件；长任务用待办列表、压缩或子Agent做大范围搜索。
- 可验证的反馈信号（测试、lint、类型检查）是代码Agent效果好的关键。
- 安全：沙箱执行、限制网络，危险命令（`rm -rf`、`git push --force`、部署）需确认，不暴露生产凭证，git可回滚，人工代码审查后合并。
- 评估：SWE-bench类任务加内部真实issue，看测试通过率、改动是否最小、有无修改测试等投机行为。

Q4：***设计一个深度研究Agent（Deep Research Agent）***

- **用编排者-工作者架构：必要时先澄清范围，主Agent把问题拆成独立子方向，并行派子Agent各自搜索阅读并只返回精炼发现和来源，主Agent汇总、补缺口，最后撰写带引用的报告并核对引用。**
- 关键挑战：来源可信度、信息冲突、重复搜索、token成本高、网页里的间接提示注入。
- 工程上持久化中间结果以便续跑，控制子Agent数量和搜索预算，长任务给进度反馈。
- 评估：事实准确性、引用准确性、覆盖面、来源质量，用LLM-as-judge加评分标准，再人工抽检。

Q5：***如何降低Agent的延迟？***

- **最有效的是流式输出、并行和减少模型往返，再配合模型路由和提示缓存。**
- 流式：尽早展示文本和进度（如"正在查询订单……"），降低感知延迟。
- 并行：并行工具调用、并行子Agent、护栏与主模型并行。
- 小模型处理简单步骤；提示缓存降低首token延迟。
- 合并常用工具操作、确定性步骤用代码实现；预取可能用到的数据，对相同或相似查询复用结果（注意时效和个性化）。

Q6：***什么是提示缓存（Prompt Caching）？在Agent中如何利用？***

- **服务端缓存提示前缀的计算结果（KV cache），后续请求只要前缀完全相同就能复用，降低输入成本和首token延迟；Agent每轮都重发系统提示、工具定义和历史，天然适合。**
- 稳定内容放前面（工具定义 → 系统提示 → 长文档 → 对话历史），变化内容放最后。
- 前缀里不要放时间戳、随机ID；工具列表和顺序保持稳定，动态增删工具会让缓存失效。
- 缓存有TTL，厂商用法不同（显式断点或自动）；上下文压缩会改变前缀，要权衡压缩频率与命中率。

Q7：***Agent系统中应设计哪些降级（Fallback）策略？***

- **在模型、工具、任务、质量和预算各层都要有降级路径，并且所有降级都要记录监控。**
- 模型层：主模型超时、限流或故障时切换备用模型或厂商。
- 工具层：先重试，仍失败则让模型换替代工具或求助用户。
- 任务层：完不成时返回部分结果并说明缺口，或转人工；质量层：校验不通过时重新生成或返回安全默认回复。
- 预算层：超预算时停止并汇报进度，而不是无限运行。

Q8：***在系统设计中，如何设计护栏（Guardrails）体系？***

- **分层设计：输入层、模型层、动作层、输出层各自把关，并在严格度和误拒之间权衡。**
- 输入层：身份验证、限流、越狱注入检测、话题范围、PII检测；模型层：清晰的系统提示和行为规范。
- 动作层：参数校验、权限检查、高风险人工审批、沙箱执行；输出层：有害内容、政策合规、事实依据、格式校验。
- 用便宜快速模型并行检查，只对高风险场景用更重的检查；护栏本身也要用评估集衡量误报和漏报。

Q9：***如何为Agent选择模型？***

- **按任务难度、延迟和成本权衡：编排规划和复杂推理用最强模型（可开思考），大量简单子任务用小而快的模型。**
- 重点看工具调用、长上下文和指令遵循能力，而不只是通用排行榜。
- 在自己的评估集上比较成功率、成本和延迟。
- 抽象模型接口，保持模型可替换，方便升级和降级。

Q10：***长时间运行（数小时）的Agent任务需要考虑什么？***

- **最重要的是状态持久化和检查点，让中断后能恢复而不是从头开始；其次是上下文管理和进度可见性。**
- 上下文：压缩、外部笔记、子Agent，避免溢出和质量下降。
- 后台异步执行，完成后通知，允许用户中途查看和干预。
- 设预算和超时防失控；保持沙箱环境可复现，能检测外部依赖变化。

Q11：***如何设计Agent的记忆系统以支持个性化？***

- **区分会话内记忆（上下文）和跨会话记忆（偏好、历史事实）：会话结束时或通过记忆工具抽取值得记的信息，按用户隔离存储，新会话时检索相关记忆或让Agent按需查询。**
- 处理记忆冲突和过期。
- 允许用户查看、修改和删除记忆。
- 记忆内容视为数据而非指令，防止被注入恶意指令。

Q12：***如何设计Agent的评估与迭代流程？***

- **建立离线评估集并在每次改动时自动运行，线上追踪所有轨迹，把新发现的失败加回评估集，形成"发现 → 修复 → 回归测试"闭环。**
- 评估集包含真实任务、边界情况和对抗样本，结合确定性检查、LLM-as-judge和人工评审。
- 线上监控成功率、延迟、成本和用户反馈。
- 抽样分析失败轨迹，定位是提示、工具、检索还是模型能力问题；用A/B测试或灰度发布验证线上效果。

Q13：***如何设计一个能操作浏览器/电脑的Agent（Computer Use）？***

- **用截图加可访问性树/DOM感知页面，输出点击、输入、滚动等动作，在隔离的虚拟机或浏览器里运行，关键操作人工确认；有API时优先用API。**
- 挑战：步骤多、延迟高、页面动态变化、坐标定位误差、网页提示注入。
- 安全：不登录敏感账号或用专用账号，限制可访问域名，付款和提交表单需确认。

Q14：***Agent系统中的多租户与扩展性问题如何处理？***

- **租户之间的数据、记忆、索引和沙箱彻底隔离，按租户限流配额，编排服务做成无状态以便水平扩展。**
- 会话状态放在外部数据库或缓存中。
- 长任务走任务队列异步执行，不占用请求连接。
- 模型API限流用重试退避和多区域/多供应商分流处理。
