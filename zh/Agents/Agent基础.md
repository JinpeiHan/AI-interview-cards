# Agent基础

Q1：***什么是LLM Agent（大模型智能体）？***

- LLM Agent是以大语言模型为“大脑”、能够**自主决定下一步行动**的系统：模型在一个循环中观察环境、推理、调用工具（搜索、代码执行、API等），根据工具返回的结果继续决策，直到完成目标或满足停止条件。
- 一个常见的简化定义：**Agent = LLM + 工具 + 循环（loop）+ 记忆**。
- 与普通聊天机器人的核心区别是：Agent的**控制流由模型动态决定**，而不是由开发者预先写死。

Q2：***Agent和Workflow（工作流）/Chain（链）有什么区别？***

- **Workflow/Chain**：LLM和工具按照**预定义的代码路径**编排，例如“先分类→再检索→再生成”。步骤固定、可预测、易测试。
- **Agent**：LLM**自己决定**调用哪些工具、调用几次、以什么顺序，步骤数量事先未知。
- 二者是一个连续谱：从单次调用 → 提示链（prompt chaining）→ 路由（routing）→ 并行化（parallelization）→ 编排者-工作者（orchestrator-workers）→ 完全自主的Agent，**自主性越高，灵活性越高，但成本、延迟和不可预测性也越高**。

Q3：***常见的Workflow模式有哪些？***

- **提示链（Prompt chaining）**：把任务拆成固定的顺序步骤，上一步输出作为下一步输入，中间可加程序化检查（gate）。
- **路由（Routing）**：先对输入分类，再分发给专门的提示或模型（如简单问题给小模型，复杂问题给大模型）。
- **并行化（Parallelization）**：分段（sectioning）并行处理独立子任务，或投票（voting）多次运行取共识。
- **编排者-工作者（Orchestrator-workers）**：中心LLM动态拆分子任务并分派给工作者LLM，再汇总结果。
- **评估者-优化者（Evaluator-optimizer）**：一个LLM生成，另一个LLM评估并给出反馈，循环迭代改进。

Q4：***描述Agent的基本循环（Agent Loop）***

1. 接收用户目标，与系统提示、工具定义一起构成上下文；
2. LLM推理并输出：要么是**最终回答**，要么是一个或多个**工具调用**；
3. 运行时（harness）执行工具调用，把**工具结果（observation）**追加到上下文；
4. 回到第2步，直到模型给出最终回答、达到最大步数/预算，或触发人工介入。

- 关键点：模型本身不执行任何操作，**真正执行工具的是外部运行时**；循环的终止条件、预算和错误处理都需要在运行时中显式设计。

Q5：***什么是ReAct？它的优点和缺点是什么？***

- **ReAct（Reasoning + Acting）**：让模型交替输出**Thought（思考）→ Action（行动）→ Observation（观察）**，把推理过程与外部交互交织在一起。
- 优点：
    - 推理可以根据真实观察动态调整，减少纯CoT中的**幻觉和错误传播**；
    - 轨迹可读，便于调试和解释。
- 缺点：
    - 每步都要调用一次LLM，**延迟和token成本高**；
    - 容易陷入循环（重复调用同一工具）或过早结束；
    - 长轨迹会撑大上下文。
- 现代模型的原生function calling和“交错思考（interleaved thinking）”本质上是ReAct思想的工程化实现。

Q6：***什么是Plan-and-Execute（规划-执行）模式？与ReAct相比如何？***

- 先由**规划器（planner）**生成完整的多步计划，再由**执行器（executor）**逐步执行，必要时**重新规划（replan）**。
- 相比ReAct：
    - 优点：全局视角更好，可以对计划做审核；执行步骤可以用更便宜的模型甚至并行执行，**减少大模型调用次数**；
    - 缺点：初始计划可能基于错误假设，如果环境变化快而不及时重新规划，会**执行过时的计划**。
- 实践中常把两者结合：高层计划 + 每步内部用ReAct式循环。

Q7：***什么是Reflection（反思）？有哪些典型方法？***

- Reflection指Agent**对自己的输出或轨迹进行批判和修正**，以提高质量。
- 典型方法：
    - **Self-Refine**：生成 → 自我反馈 → 改进，迭代若干轮；
    - **Reflexion**：任务失败后用语言总结失败原因，存入记忆，在下一次尝试中参考（“语言化的强化学习信号”）；
    - **评估者-优化者**：用独立的评估模型或外部信号（单元测试、编译器、校验器）提供反馈。
- 注意：**没有外部反馈的纯自我反思效果有限**，模型可能无法发现自身错误，甚至把对的改错；有可验证的信号（测试、执行结果）时反思最有效。

Q8：***Agent的记忆分为哪几类？***

- **短期记忆（工作记忆）**：当前会话的上下文窗口，包括对话历史、工具调用和结果。受限于上下文长度。
- **长期记忆**：跨会话持久化的信息，通常存储在外部（向量库、数据库、文件），需要时检索回上下文。常进一步细分为：
    - **情景记忆（episodic）**：过去发生的交互和经历；
    - **语义记忆（semantic）**：事实与知识，如用户偏好；
    - **程序性记忆（procedural）**：如何做事，如系统提示、技能、学到的规则。
- 此外，模型权重本身可视为**参数化记忆**。

Q9：***Agent由哪些核心组件构成？***

- **模型**：负责推理与决策；
- **工具**：与外部世界交互的接口（API、代码执行、浏览器、文件系统等）；
- **指令/系统提示**：定义角色、目标、约束和行为规范；
- **记忆与上下文管理**：决定什么信息进入上下文；
- **运行时（harness/orchestration）**：执行循环、调用工具、处理错误、限制预算、记录日志；
- **护栏（guardrails）**：输入输出检查、权限控制、人工审批。

Q10：***什么时候不应该使用Agent？***

- 任务步骤**固定且可预知**时，用Workflow或普通代码更便宜、更可靠、更易测试；
- 单次LLM调用 + 检索 + 少量示例就能解决的问题；
- 对**延迟和成本**极其敏感的场景（Agent通常要多次调用模型）；
- 错误代价高且**难以验证或回滚**的操作，而又无法加入人工审核；
- 缺乏良好工具和评估手段时，Agent的行为难以调试。
- 原则：**从最简单的方案开始，只有在确有必要（开放式、步骤不可预知的问题）时才增加自主性。**

Q11：***什么样的任务适合用Agent？***

- **开放式问题**，难以或无法预先写死步骤数量和路径；
- 需要与环境多轮交互、根据反馈调整，如编码、调研、数据分析、复杂客服；
- 结果**可以验证**（测试是否通过、答案是否可查证），便于Agent自我纠错；
- 对一定的延迟和成本可以接受，且有足够的信任与沙箱支持模型自主操作。

Q12：***为什么说“上下文工程（Context Engineering）”是Agent开发的核心？***

- 模型的每一步决策只依赖于当前上下文，因此**放入什么信息、以什么格式、放多少**决定了Agent的上限。
- 上下文是有限资源：内容过多会导致成本升高、注意力分散、关键信息被淹没（常称为“上下文腐化”，context rot）。
- 常见手段：精简系统提示、按需检索（just-in-time）、工具结果截断/摘要、上下文压缩（compaction）、外部笔记（如待办文件）、子Agent隔离上下文。
- 提示工程关注“怎么写一条好提示”，上下文工程关注“**在整个循环中如何管理进入模型的全部token**”。

Q13：***Agent中的“工具”和“动作空间”应如何设计？***

- 工具是Agent与环境交互的唯一途径，可视为**Agent-计算机接口（ACI）**，其设计重要性不亚于提示本身。
- 原则：
    - 工具数量**少而精**，功能不重叠，避免模型选择困难；
    - 名称、描述、参数清晰，像给新员工写文档一样写工具说明；
    - 返回**高信号**的结果，避免返回大量无关数据；
    - 让错误难以发生（poka-yoke），例如要求绝对路径而不是相对路径。

Q14：***如何控制Agent的终止条件，避免无限循环？***

- 设置**最大步数/最大工具调用次数**、**token或费用预算**、**超时时间**；
- 检测重复动作（同一工具同一参数被反复调用）并中止或提示模型换策略；
- 在提示中明确“完成”的标准，并提供显式的“完成/提交答案”工具；
- 在关键节点设置**人工检查点**；
- 达到上限时优雅退出：返回部分结果和当前进度，而不是静默失败。

Q15：***Agent常见的失败模式有哪些？***

- **幻觉工具调用**：调用不存在的工具或编造参数；
- **循环/卡死**：重复同一动作；
- **过早结束**：没完成就宣称完成；
- **目标漂移**：在长任务中逐渐偏离原始目标；
- **错误累积**：早期错误被后续步骤放大（复合误差，每步成功率为$p$时，$n$步全成功的概率约为$p^n$）；
- **上下文溢出**：工具结果太长，挤掉关键信息；
- **被提示注入劫持**：执行了来自网页/文档中的恶意指令。

Q16：***单Agent和多Agent如何选择？***

- 默认**先用单Agent**：架构简单、上下文统一、易调试；
- 当任务可以**高度并行**（如广度调研）、单个上下文装不下、或需要严格隔离不同职责/权限时，再考虑多Agent；
- 多Agent会带来**更高的token消耗**、协调开销和新的失败模式（信息丢失、重复劳动）。

Q17：***Agent框架（如LangGraph、各厂商的Agent SDK等）的作用是什么？是否必须使用？***

- 框架提供通用能力：Agent循环、工具注册、状态管理、记忆、追踪、多Agent编排、人工介入等，能加快原型开发。
- 缺点：抽象层可能**隐藏底层提示和响应**，增加调试难度，并诱导过度设计。
- 建议：**先直接使用模型API实现**（核心循环只需几十行代码），理解底层机制后再按需选用框架；使用框架时要确保理解其底层行为。
