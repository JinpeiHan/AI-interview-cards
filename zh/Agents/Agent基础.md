# Agent基础

Q1：***什么是LLM Agent（大模型智能体）？***

- **LLM Agent是以大模型为"大脑"、在循环中自主决定下一步行动的系统：观察、推理、调用工具，再根据结果继续决策，直到完成目标。**
- 常见简化定义：Agent = LLM + 工具 + 循环 + 记忆。
- 与普通聊天机器人的区别：控制流由模型动态决定，而不是开发者写死。

Q2：***Agent和Workflow（工作流）/Chain（链）有什么区别？***

- **Workflow按预定义的代码路径编排LLM和工具，步骤固定、可预测；Agent由LLM自己决定调用什么工具、调用几次、什么顺序。**
- 二者是连续谱：单次调用 → 提示链 → 路由 → 并行 → 编排者-工作者 → 完全自主Agent。
- 自主性越高越灵活，但成本、延迟和不可预测性也越高。

Q3：***常见的Workflow模式有哪些？***

- **常见的有五种：提示链、路由、并行化、编排者-工作者、评估者-优化者。**
- 提示链：固定顺序步骤，上一步输出喂给下一步，中间可加程序化检查。
- 路由：先分类，再分发给专门的提示或模型（简单问题给小模型）。
- 并行化：独立子任务并行（sectioning），或多次运行投票（voting）。
- 编排者-工作者：中心LLM动态拆任务、分派、汇总；评估者-优化者：一个生成、一个评估反馈，循环改进。

Q4：***描述Agent的基本循环（Agent Loop）***

- **模型拿到目标、系统提示和工具定义后，输出最终回答或工具调用；运行时执行工具并把结果追加回上下文，再让模型继续，直到给出答案或触发停止条件。**
- 模型本身不执行任何操作，真正执行工具的是外部运行时（harness）。
- 终止条件（最大步数、预算、人工介入）和错误处理必须在运行时里显式设计。

Q5：***什么是ReAct？它的优点和缺点是什么？***

- **ReAct让模型交替输出"思考 → 行动 → 观察"，把推理和外部交互交织在一起，推理能根据真实反馈调整。**
- 优点：比纯CoT更少幻觉和错误传播；轨迹可读，便于调试。
- 缺点：每步一次LLM调用，延迟和成本高；容易循环或过早结束；长轨迹撑大上下文。
- 现代模型的原生function calling和交错思考本质上就是ReAct的工程化实现。

Q6：***什么是Plan-and-Execute（规划-执行）模式？与ReAct相比如何？***

- **先由规划器生成完整计划，再由执行器逐步执行，必要时重新规划。**
- 优点：全局视角更好、计划可审核；执行可用便宜模型或并行，减少大模型调用。
- 缺点：初始计划可能基于错误假设，环境变化快时容易执行过时计划。
- 实践中常结合：高层计划 + 每步内部用ReAct循环。

Q7：***什么是Reflection（反思）？有哪些典型方法？***

- **Reflection是Agent批判并修正自己的输出或轨迹来提高质量，最有效的前提是有外部可验证的反馈。**
- Self-Refine：生成 → 自我反馈 → 改进，迭代几轮。
- Reflexion：失败后用语言总结原因存入记忆，下次尝试参考。
- 评估者-优化者：用独立评估模型或测试、编译器等外部信号给反馈。
- 没有外部信号的纯自我反思效果有限，甚至可能把对的改错。

Q8：***Agent的记忆分为哪几类？***

- **分为短期记忆（当前上下文窗口）和长期记忆（存在外部、跨会话、按需检索回上下文）。**
- 长期记忆常细分为：情景记忆（过去的交互）、语义记忆（事实和用户偏好）、程序性记忆（怎么做事，如技能、规则）。
- 模型权重本身可视为参数化记忆。

Q9：***Agent由哪些核心组件构成？***

- **模型、工具、指令、记忆与上下文管理、运行时、护栏。**
- 模型负责推理决策；工具是与外界交互的接口；系统提示定义角色、目标和约束。
- 记忆与上下文管理决定什么信息进入上下文。
- 运行时负责跑循环、执行工具、处理错误和预算；护栏负责输入输出检查、权限和人工审批。

Q10：***什么时候不应该使用Agent？***

- **步骤固定可预知、或单次LLM调用加检索就能解决时，不该用Agent；原则是从最简单方案开始，确有必要才增加自主性。**
- 对延迟和成本极敏感的场景（Agent要多次调用模型）。
- 错误代价高、难以验证或回滚，又无法加人工审核的操作。
- 缺乏好的工具和评估手段时，Agent行为难以调试。

Q11：***什么样的任务适合用Agent？***

- **开放式、步骤和路径无法预先写死、需要与环境多轮交互并根据反馈调整的任务，如编码、调研、数据分析。**
- 结果可验证（测试能否通过、答案可查证），Agent能自我纠错。
- 能接受一定延迟和成本，并有足够的沙箱和信任让模型自主操作。

Q12：***为什么说“上下文工程（Context Engineering）”是Agent开发的核心？***

- **模型每一步只依据当前上下文做决策，所以放什么、怎么放、放多少直接决定Agent的上限。**
- 上下文是有限资源：内容太多会增加成本、分散注意力、淹没关键信息（上下文腐化）。
- 常用手段：精简系统提示、按需检索、截断或摘要工具结果、上下文压缩、外部笔记、子Agent隔离。
- 提示工程关注写好一条提示；上下文工程关注整个循环中进入模型的全部token。

Q13：***Agent中的“工具”和“动作空间”应如何设计？***

- **工具是Agent与环境交互的唯一途径（Agent-计算机接口，ACI），要像给新员工写文档一样认真设计。**
- 少而精、功能不重叠，避免模型选择困难。
- 名称、描述、参数清晰；返回高信号结果，不塞无关数据。
- 防呆设计（poka-yoke），让错误难以发生，如要求绝对路径。

Q14：***如何控制Agent的终止条件，避免无限循环？***

- **在运行时设硬上限（最大步数、token或费用预算、超时），并让模型明确知道什么算"完成"。**
- 检测重复动作（同工具同参数反复调用），中止或提示换策略。
- 提供显式的"完成/提交答案"工具，关键节点设人工检查点。
- 到达上限时优雅退出，返回部分结果和进度而不是静默失败。

Q15：***Agent常见的失败模式有哪些？***

- **常见的有：幻觉工具调用、循环卡死、过早结束、目标漂移、错误累积、上下文溢出、被提示注入劫持。**
- 错误累积最致命：早期小错被后续步骤放大，长任务的成功率随步数指数下降。
- 上下文溢出：工具结果太长，挤掉关键信息。
- 提示注入：执行了网页或文档里的恶意指令。
- 核心公式：每步成功率为$p$时，$n$步全成功概率约为$p^n$

Q16：***单Agent和多Agent如何选择？***

- **默认先用单Agent，架构简单、上下文统一、易调试；只有任务高度可并行、单个上下文装不下或需要隔离职责权限时才用多Agent。**
- 多Agent的代价：token消耗更高、协调开销、信息丢失和重复劳动等新失败模式。

Q17：***Agent框架（如LangGraph、各厂商的Agent SDK等）的作用是什么？是否必须使用？***

- **不是必须的。框架提供循环、工具注册、状态、记忆、追踪、多Agent编排等通用能力，能加速原型开发。**
- 缺点：抽象层会隐藏底层提示和响应，调试更难，还容易诱导过度设计。
- 建议先直接用模型API实现（核心循环几十行代码），理解机制后再按需选框架。
