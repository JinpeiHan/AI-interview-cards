# 评估与安全

Q1：***为什么Agent的评估比普通LLM评估更难？***

- **Agent是多步、非确定性的，会改变环境，正确路径也不唯一，所以不能像普通LLM那样只比对一次文本输出。**
- 同一任务每次轨迹不同，一次运行不代表整体表现。
- 正确做法有很多种，不能和"标准轨迹"逐步比对。
- 需要可复现、可重置的环境（数据库、网页、代码仓库），并检查最终状态。
- 成本高：一个样例可能涉及几十次模型调用。

Q2：***Agent评估有哪些主要维度和方法？***

- **主要看结果（任务是否完成）、轨迹（过程是否合理合规）、效率、可靠性和安全性，方法上把确定性代码检查、LLM-as-judge和人工评估结合起来。**
- 结果：测试是否通过、数据库最终状态、答案是否正确。
- 轨迹：工具选择和参数是否合理，有无多余或危险步骤。
- 效率：步数、工具调用、token、耗时、费用。
- 可靠性用多次运行衡量：pass@k是k次中至少一次成功，pass^k是k次全部成功，后者更反映生产可靠性。

Q3：***什么是LLM-as-Judge？如何正确使用？***

- **用一个LLM按评分标准（rubric）评估另一个模型或Agent的输出和轨迹，可扩展、便宜、能评开放式输出，但有已知偏差需要校准。**
- 偏差：位置偏差、冗长偏差、自我偏好、受表面格式影响。
- 评分标准要具体，最好是二元或少数几档；让评审先给理由再打分。
- 成对比较时交换顺序评两次；用人工标注样本校准，计算与人类的一致率。
- 能用确定性检查（测试、精确匹配）的地方优先用确定性检查。

Q4：***介绍几个常见的Agent基准测试（Benchmark）***

- **最常被提到的是SWE-bench（软件工程）、τ-bench（客服对话加工具调用）、WebArena（网页操作）和GAIA（通用助手）。**
- SWE-bench：修真实GitHub issue，用仓库测试判定，有人工筛选的Verified子集。
- τ-bench：与模拟用户对话、调用领域API并遵守业务策略，按数据库最终状态评估，强调pass^k。
- WebArena：在自托管真实网站中完成任务；GAIA：多步推理、搜索、文件和多模态问题，答案简短易自动评分。
- 其他有OSWorld、Terminal-Bench、BrowseComp；公开基准有数据污染且和业务不匹配，生产中要建自己的评估集。

Q5：***如何为自己的Agent构建评估集？***

- **从真实用户请求和失败案例中收集任务，给每个任务定义可自动检查的成功标准，从几十个高质量样例起步并持续扩充。**
- 覆盖常见场景、边界情况和对抗样本。
- 区分能力评估（衡量上限，通过率可以低）和回归评估（防退化，应接近100%）。
- 每次改提示、工具或模型都自动运行，跟踪指标变化。

Q6：***什么是Agent的可观测性（Observability）？需要记录什么？***

- **可观测性是能看清Agent每一步做了什么、为什么这么做，是调试、评估和合规的基础，核心是完整的tracing。**
- 记录每次模型调用的完整输入、输出和思考内容（如可用）。
- 记录每次工具调用的名称、参数、结果、耗时和错误，以及token、延迟、费用。
- 记录多Agent间的调用关系（span树）、用户反馈和最终结果。
- 工具有OpenTelemetry、LangSmith、Langfuse、Arize Phoenix等；日志里的敏感数据要脱敏。

Q7：***什么是提示注入（Prompt Injection）？直接注入和间接注入有什么区别？***

- **提示注入是攻击者构造输入，让模型忽略原有指令转而执行攻击者的指令。**
- 直接注入：用户自己在输入里写恶意指令，如"忽略之前的所有指令"，越狱也属此类。
- 间接注入：恶意指令藏在Agent处理的外部数据里，如网页、邮件、文档、工具返回结果。
- 对Agent来说间接注入更危险，因为它会自动读取大量不可信内容，且拥有执行真实操作的工具。

Q8：***如何防御提示注入？***

- **没有完美防御，只能多层纵深防御，核心是限制被劫持后能造成的破坏。**
- 最小权限；隔离不可信数据，处理不可信内容的模块不直接拥有高权限工具（如双LLM模式）。
- 避免"致命三要素"同时存在：访问私有数据 + 接触不可信内容 + 能对外通信。
- 敏感操作人工确认，出站网络只允许白名单域名。
- 用分类器检测注入和数据外泄，并选用对注入更鲁棒的模型。

Q9：***为什么Agent需要沙箱（Sandboxing）？常见的沙箱方案有哪些？***

- **Agent会执行代码、命令和文件操作，模型出错或被注入可能删数据、泄露凭证、破坏系统，沙箱把影响限制在可控环境里。**
- 容器（Docker）：轻量，但共享宿主内核，隔离较弱；gVisor、微虚拟机（Firecracker）隔离更强。
- 操作系统级沙箱：Linux的seccomp/Landlock/bubblewrap、macOS的Seatbelt；运行不可信代码也可用WebAssembly。
- 关键配置：文件系统只能访问工作目录、网络白名单、资源限制，不在沙箱里放敏感凭证。

Q10：***Agent的权限系统应如何设计？***

- **遵循最小权限：默认只读，按操作风险分级授权，高风险操作必须人工确认。**
- 低风险（读、搜索）自动允许；中风险（改文件、调内部API）按规则允许或询问；高风险（删除、付款、对外发消息、生产部署）必须确认。
- 支持可配置的允许/拒绝规则。
- 用短期、细粒度、按任务签发的凭证，而不是长期管理员密钥；所有操作留审计日志。

Q11：***什么是Human-in-the-Loop（人在回路）？在Agent中如何应用？***

- **在Agent执行的关键节点引入人工审核、确认或纠正。**
- 常见方式：高风险操作前审批、信息不足时澄清、执行前审核计划、交付前审核结果、无法处理时升级给人工。
- 权衡：介入太多会降效率并造成"审批疲劳"（不看就点同意），所以只放在真正高风险的节点。

Q12：***什么是护栏（Guardrails）？有哪些类型？***

- **护栏是在模型之外对输入、输出和动作做检查和约束的机制，分为输入、输出和动作三类。**
- 输入护栏：检测越狱、提示注入、离题请求、PII。
- 输出护栏：检测有害内容、幻觉、敏感信息泄露，做格式校验。
- 动作护栏：工具执行前检查参数和权限，如金额上限、禁止路径。
- 实现可以是规则、分类模型或LLM审核，可与主模型并行运行以降低延迟。

Q13：***如何控制Agent的成本？***

- **最有效的是模型路由、提示缓存和上下文管理，再加上硬性预算上限和成本监控。**
- 模型路由：简单子任务用小模型，复杂推理才用大模型。
- 提示缓存：把稳定的系统提示、工具定义、长文档放在前缀缓存。
- 上下文管理：截断摘要工具结果、压缩历史；按需调节思考预算，非实时任务用批处理API。
- 设每个任务的步数、token和费用上限，按用户和任务类型监控成本，及时发现循环导致的激增。

Q14：***什么是“奖励投机（Reward Hacking）”？在Agent中有哪些表现？***

- **模型找到满足评估信号的捷径，而没有真正完成任务。**
- 典型表现：为了测试通过而修改或删除测试、硬编码期望输出。
- 宣称完成但实际没完成，或绕过而不是解决权限、校验问题。
- 应对：更全面的评估（隐藏测试、检查代码改动），轨迹评估中专门查这类行为，提示里明确禁止。

Q15：***Agent上线前后应如何持续保证质量与安全？***

- **上线前做离线评估、红队测试和灰度发布；上线后持续监控、抽样审查，并把新失败案例加回评估集形成闭环。**
- 红队重点测提示注入、越权和滥用。
- 线上监控成功率、错误率、延迟、成本和用户反馈，对轨迹抽样做LLM-as-judge和人工审查。
- 模型或提示更新时跑回归评估，并能快速回滚。

Q16：***Agent中的数据隐私问题有哪些？如何处理？***

- **主要风险是用户数据流进日志、长期记忆和第三方工具，以及跨用户泄露和通过注入外泄。**
- 日志和追踪中对PII脱敏。
- 按用户/租户隔离记忆和检索索引。
- 审查第三方工具的数据处理协议，遵守数据保留和删除策略，限制Agent的对外通信能力。
