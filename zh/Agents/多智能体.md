# 多智能体

Q1：***什么是多智能体系统（Multi-Agent System）？***

- **由多个LLM Agent协作完成任务的系统，每个Agent可以有不同的角色、提示、工具、模型和权限，通过消息、共享状态或工具调用协作。**
- 动机：分工与专业化、并行加速、突破单个上下文窗口、隔离职责和权限。

Q2：***常见的多Agent架构有哪些？***

- **最常见的是编排者-工作者：主Agent拆任务分给多个工作者并汇总；此外还有监督者/层级式、交接、顺序流水线、辩论和去中心化网络。**
- 监督者/层级式：监督者根据状态决定把控制权交给哪个专业Agent，可多层嵌套。
- 交接（Handoff）：直接把对话移交给更合适的Agent，如分诊Agent交给退款Agent。
- 顺序流水线：研究员 → 写手 → 审稿人；辩论：多个Agent互相批判后由裁判或共识定结论。
- 去中心化（Swarm）：点对点通信，没有中心控制者。

Q3：***Orchestrator-Worker模式是如何工作的？优缺点是什么？***

- **编排者分析任务并拆成子任务，给每个子任务写清指令后启动工作者；工作者在各自独立的上下文中执行并返回精炼结果，编排者汇总，必要时再开一轮。**
- 子任务指令要包含目标、输出格式、可用工具和边界。
- 优点：易并行、上下文隔离、编排者保持全局视图。
- 缺点：编排者是瓶颈和单点故障；指令不清会导致重复或偏题；token消耗大。

Q4：***什么是子Agent（Subagent）？为什么说它能实现“上下文隔离”？***

- **子Agent是主Agent启动的、拥有独立上下文窗口的Agent，用来完成边界清晰的子任务；它探索时读到的大量文件和工具输出只留在自己的上下文里，主Agent只收到精炼摘要。**
- 好处：主Agent上下文保持干净（缓解上下文腐化），可并行运行多个子Agent，可配不同工具、权限或更便宜的模型。
- 代价：主Agent看不到细节，摘要遗漏会影响后续决策；启动子Agent本身也有开销。

Q5：***多Agent之间如何通信？***

- **主要方式是消息传递、共享状态（黑板）、共享文件系统、把Agent包装成工具，以及标准协议。**
- 消息：自然语言或结构化JSON互发请求和结果。
- 共享文件：子Agent把详细结果写进文件、只返回路径，避免"传话"丢信息。
- Agent-as-tool：把一个Agent包装成另一个可调用的工具。
- 协议：A2A用于不同厂商/框架的Agent互相发现与协作；MCP主要连接Agent与工具/数据。

Q6：***多Agent系统的成本和延迟有什么特点？***

- **token成本通常显著高于单Agent（数倍甚至更多），因为每个Agent都有自己的系统提示、工具定义和上下文；延迟则取决于能否并行。**
- 广度型任务并行执行可以降低总耗时，但串行的协调、交接、汇总会增加延迟。
- 所以多Agent适合价值高、可并行、信息量大的任务；强依赖、需紧密共享上下文的任务（如大多数编码修改）单Agent更划算。

Q7：***什么时候应该使用多Agent，什么时候不应该？***

- **适合广度优先、可并行、信息量超出单个上下文、需要不同工具权限分工或需要独立审查视角的任务；不适合子任务强依赖、需要高度一致产出、或成本延迟敏感的简单任务。**
- 独立审查的典型例子是生成者与审核者分离。
- 高度一致性的反例：多个Agent并行写同一份代码，风格和假设容易冲突。

Q8：***多Agent系统有哪些典型的失败模式？***

- **最常见的是任务描述不清和信息在传递中丢失，此外还有决策冲突、过度生成Agent、循环死锁、角色混淆、缺乏验证和错误级联。**
- 描述不清：工作者重复工作、遗漏或理解偏差；传话丢失：摘要丢掉关键细节。
- 决策冲突：并行Agent做了相互矛盾的隐式假设，合并时不一致。
- 循环死锁：互相交接或互相等待；缺乏验证：没人对最终结果负责，错误层层传递成级联。

Q9：***如何提升多Agent系统的可靠性？***

- **关键是编排者的委派质量：给子Agent的指令要写清目标、输出格式、可用工具和信息源、任务边界和何时停止。**
- 按任务复杂度决定投入规模，简单问题少派子Agent。
- 用结构化输出和共享文件减少信息损失，加入专门的验证Agent或测试检查。
- 完整追踪每个Agent的输入输出和工具调用；长任务支持检查点和断点续跑。
- 通过评估迭代编排者提示，很多问题源于委派方式。

Q10：***什么是多Agent辩论（Multi-Agent Debate）？有什么作用？***

- **多个Agent各自给出答案，再阅读彼此回答并反驳或修正，若干轮后由裁判或投票定结论，在部分推理和事实性任务上能提升准确性。**
- 局限：成本高。
- 同一模型的多个实例可能共享偏差，容易从众趋同到错误答案。
- 相同计算预算下，收益不一定优于自洽性投票等更简单的方法。

Q11：***Agent之间“交接（Handoff）”应如何设计？***

- **把交接做成一个工具（如`transfer_to_refund_agent`）由模型决定何时调用，并在交接时传递必要上下文，避免用户重复描述。**
- 传递的上下文包括用户信息、已收集的信息和问题摘要。
- 职责边界要清晰，防止来回踢皮球。
- 提供交回主Agent或转人工的路径。

Q12：***多Agent系统中如何管理共享状态？***

- **要有单一事实来源（数据库、共享文件或编排者维护的状态对象），并控制并发写入。**
- 并发写加锁或用只追加日志，避免竞态。
- 每个Agent只读取任务所需的状态，避免上下文膨胀。
- 状态变更做版本化和记录，便于回溯调试。

Q13：***如何评估多Agent系统？***

- **主要看端到端结果（任务成功率、答案质量），再辅以过程指标和轨迹分析，并与单Agent基线对比确认多花的成本值得。**
- 过程指标：子Agent数、工具调用数、token、耗时、重复工作比例。
- 轨迹分析：委派是否合理、信息是否在传递中丢失。
- 多Agent非确定性强，应评估是否达成目标，而不是要求固定执行步骤。

Q14：***多Agent系统中如何处理权限与安全？***

- **核心是最小权限和隔离：每个Agent只拥有职责所需的工具权限，处理不可信输入的Agent与高权限Agent隔离，二者之间只传受约束的结构化数据。**
- 防止提示注入在Agent之间传播，来自其他Agent的消息也不完全可信。
- 高风险动作保留人工审批。
