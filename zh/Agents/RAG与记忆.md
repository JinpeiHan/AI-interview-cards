# RAG与记忆

Q1：***什么是RAG（检索增强生成）？为什么需要它？***

- **RAG是在生成前先从外部知识库检索相关内容放进提示，让LLM基于这些内容回答。**
- 弥补模型知识的截止日期，并接入它不了解的私有/领域数据。
- 减少幻觉，并能给出引用来源。
- 相比微调，更新知识只需更新索引，成本低、可控、可删除。

Q2：***描述一个典型的RAG流程***

- **分离线索引和在线查询两部分：离线把文档切块、编码成向量存库；在线检索相关块、重排后和问题一起交给LLM生成。**
- 离线：解析文档 → 清洗与切块 → embedding编码 → 存入向量库（同时可建关键词索引和元数据）。
- 在线：查询改写 → 向量 + 关键词检索Top-K → 重排序筛选 → 拼进提示，生成带引用的回答。

Q3：***常见的切块（Chunking）策略有哪些？如何选择chunk大小？***

- **常见策略有固定长度加重叠、按段落标题等结构切分、语义切块，以及用LLM给每块加上下文前缀的上下文化切块；大小一般从几百token起步，用评估集调。**
- 块太小语义不完整，太大则引入噪声、稀释embedding、占用上下文。
- 结构感知切分（Markdown标题、代码函数、表格行）通常比硬切效果好。
- "小块检索、大块返回"（parent-document retrieval）可兼顾检索精度和上下文完整性。

Q4：***Embedding模型在RAG中起什么作用？如何选择？***

- **Embedding模型把文本映射成稠密向量，让语义相近的文本在向量空间里距离近，从而支持语义检索。**
- 通常是双塔结构：查询和文档分别编码，文档向量可离线预计算，检索快。
- 选择看领域和语言匹配、最大输入长度、向量维度、多语言能力，最重要的是在自己数据上的检索评估，而不只看排行榜。
- 必要时在领域数据上微调。
- 核心公式：$\cos(q,d)=\frac{q\cdot d}{\|q\|\|d\|}$

Q5：***向量检索是如何加速的？什么是ANN？***

- **精确最近邻要和所有向量比较，大规模时太慢，所以用近似最近邻（ANN），牺牲少量召回换取大幅提速。**
- HNSW：分层图索引，快、召回高，但内存大。
- IVF：先聚类，查询时只搜最近的几个簇；PQ：压缩向量省内存，常和IVF结合。
- 常用工具：FAISS、Milvus、Qdrant、Weaviate、pgvector、Elasticsearch等。

Q6：***什么是混合检索（Hybrid Search）？为什么需要它？***

- **混合检索把关键词检索（如BM25）和向量检索结合起来，因为二者互补：向量擅长语义和同义改写，BM25擅长专有名词、编号、代码等精确匹配。**
- 融合方式可以是归一化后加权求和，或更常用的RRF。
- RRF只依赖排名、不需要分数校准，简单稳健。
- 核心公式：$score(d)=\sum_{i}\frac{1}{k+rank_i(d)}$

Q7：***什么是重排序（Reranking）？为什么它能提升效果？***

- **先用快速检索器召回较多候选（如Top-50~100），再用更精细的模型重新打分选出Top-K，即"召回-精排"两阶段。**
- 常用交叉编码器：把查询和文档拼在一起输入，做完整交互注意力，比双塔精确得多。
- 代价是计算量大，所以只在少量候选上用；也可用LLM做重排。

Q8：***有哪些查询端的优化方法？***

- **核心是把用户原始问题变成更适合检索的query：改写、扩展、分解和过滤。**
- 查询改写：把口语化、含指代的多轮问题改成独立完整的query。
- 多查询和查询分解：多种表述分别检索后合并，复杂问题拆成子问题检索。
- HyDE：先让LLM生成假设答案，用它的embedding去检索；Step-back：先检索更抽象的背景知识。
- 元数据过滤：按时间、来源、权限过滤。

Q9：***如何评估RAG系统？***

- **分开评估检索层和生成层，这样才能诊断问题出在"没检索到"还是"检索到了但没用好"。**
- 检索层：Recall@K、Precision@K、MRR、nDCG。
- 生成层：忠实度（是否有检索内容支撑）、答案相关性、正确性、引用准确性。
- 方法：带标注的问答评估集，结合人工评估和LLM-as-judge（Ragas等框架有现成实现）。

Q10：***什么是Agentic RAG？与传统RAG有何区别？***

- **传统RAG是固定流水线，每次检索一次直接生成；Agentic RAG把检索当作Agent的工具，由模型决定是否检索、检索什么、用哪个数据源、结果够不够。**
- 不够时可以改写查询、多跳检索，并对结果验证综合。
- 优点：能处理多跳复杂问题；缺点：延迟和成本更高、行为难预测。
- 在代码等场景，Agent常用grep、文件浏览等即时检索替代或补充向量索引。

Q11：***长上下文模型出现后，RAG还有必要吗？***

- **仍有必要，二者是互补关系。**
- 知识库通常远大于上下文窗口，全塞进去成本高、延迟大。
- 上下文过长时模型对中间信息利用变差（Lost in the Middle），噪声也会干扰推理。
- RAG便于权限控制、实时更新和引用溯源；长上下文则降低了对检索精度的要求，可以多检索一些让模型自己筛。

Q12：***Agent的长期记忆应如何设计？***

- **要设计好写入、存储、检索、更新遗忘四个环节，并保证隐私安全。**
- 写入：记用户偏好、关键事实、任务结论和经验；可由Agent通过记忆工具主动写，或会话后后台抽取总结。
- 存储：向量库、键值/关系库、知识图谱或文件笔记，按数据形态选。
- 检索：综合相关性、新近度和重要性打分；更新：处理冲突、去重合并、设过期策略。
- 安全：用户能查看删除记忆，防止通过记忆注入恶意指令或跨用户泄露。

Q13：***什么是上下文窗口管理？有哪些常用策略？***

- **Agent循环中对话历史和工具结果不断累积，会超出窗口或拖累性能，需要主动控制留在上下文里的内容。**
- 滑动窗口：只留最近N轮，简单但丢早期信息。
- 压缩（compaction）：接近上限时把历史总结成摘要，用摘要开新上下文继续。
- 清理旧工具结果；把进度和计划写入外部笔记（如`NOTES.md`）需要时读回。
- 子Agent隔离大量探索，只返回精炼结果；只存引用（路径、URL），按需加载。

Q14：***上下文压缩（Compaction）时应保留哪些信息？有什么风险？***

- **要保留原始目标和约束、关键决策及原因、当前进度和下一步、未解决的问题、重要的文件路径和标识符；冗余工具输出和已解决的中间尝试可以丢。**
- 主要风险是信息丢失：摘要漏掉了后来才发现重要的细节，或让模型重复已做过的工作。
- 缓解：保留可回查的原始日志/文件，在压缩提示里明确必须保留的内容，并用评估调整策略。

Q15：***RAG中常见的问题有哪些？如何解决？***

- **常见问题按环节分：检索不到、排名靠后、检索到但模型没用好、文档解析差、知识过时冲突、权限泄露。**
- 检索不到：改进切块、混合检索、查询改写、微调embedding；排名靠后：加reranker。
- 模型不用或用错：提示要求基于上下文作答并引用，减少噪声块。
- 解析差：表格、图片、多栏PDF用版面分析、OCR或多模态模型；过时：加时间元数据、优先新版本。
- 权限：检索阶段按用户权限（文档级ACL）过滤。

Q16：***什么是GraphRAG？适用于什么场景？***

- **GraphRAG先用LLM从文档中抽取实体和关系建成知识图谱，并做社区检测和分层摘要，检索时结合图结构和摘要。**
- 适合需要全局、跨文档综合的问题（如"这些报告的主要主题是什么"）和多跳关系推理。
- 缺点：建图成本高、更新复杂；简单事实查找用传统向量RAG通常就够。
