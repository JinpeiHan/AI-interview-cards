# RAG与记忆

Q1：***什么是RAG（检索增强生成）？为什么需要它？***

- RAG（Retrieval-Augmented Generation）是在生成之前**从外部知识库检索相关内容**，把检索结果放入提示中，让LLM基于这些内容回答。
- 解决的问题：
    - 模型知识有**截止日期**，无法获取最新信息；
    - 模型不了解**私有/领域数据**；
    - 减少**幻觉**，并可以提供**引用来源**；
    - 相比微调，更新知识只需更新索引，成本低、可控、可删除。

Q2：***描述一个典型的RAG流程***

- **离线索引（Indexing）**：
    1. 文档加载与解析（PDF、HTML、表格等）；
    2. 清洗与**切块（chunking）**；
    3. 用embedding模型把每个块编码为向量；
    4. 存入向量数据库（可同时建立关键词倒排索引和元数据）。
- **在线查询（Retrieval & Generation）**：
    1. 查询改写/扩展；
    2. 检索Top-K候选（向量检索 + 关键词检索）；
    3. **重排序（rerank）**并筛选；
    4. 把检索到的块和问题一起拼接进提示，LLM生成带引用的回答。

Q3：***常见的切块（Chunking）策略有哪些？如何选择chunk大小？***

- 策略：
    - **固定长度切块**：按token数切，配合**重叠（overlap）**避免切断语义；
    - **递归/结构化切块**：按段落、标题、句子等自然边界递归切分；
    - **语义切块**：根据相邻句子embedding的相似度变化确定边界；
    - **文档结构感知**：Markdown标题、代码函数、表格行等按结构切分；
    - **上下文化切块（contextual chunking）**：用LLM为每个块生成一段说明其在整篇文档中位置/含义的前缀，再做embedding和索引，缓解块脱离上下文的问题。
- chunk大小权衡：
    - **太小**：语义不完整，缺乏上下文；
    - **太大**：引入噪声、稀释embedding、占用上下文。
- 实践中一般从几百token起步，再用评估集调参；也可采用**“小块检索、大块返回”**（如parent-document retrieval），兼顾检索精度与上下文完整性。

Q4：***Embedding模型在RAG中起什么作用？如何选择？***

- Embedding模型把文本映射为稠密向量，使**语义相似的文本在向量空间中距离近**，常用余弦相似度$\cos(q,d)=\frac{q\cdot d}{\|q\|\|d\|}$衡量。
- 通常采用**双塔（bi-encoder）**结构：查询和文档分别编码，文档向量可以离线预计算，检索速度快。
- 选择考虑：领域与语言匹配度、最大输入长度、向量维度（存储与速度）、多语言能力、在自己数据上的检索评估结果（而不只看公开排行榜）；
- 必要时可在领域数据上**微调embedding模型**。

Q5：***向量检索是如何加速的？什么是ANN？***

- 精确的最近邻检索复杂度为$O(N)$，大规模时太慢，因此使用**近似最近邻（ANN）**算法，以少量召回损失换取大幅提速。
- 常见索引：
    - **HNSW**：基于分层可导航小世界图，速度快、召回高，但内存占用大；
    - **IVF**：先聚类，查询时只搜索最近的若干簇；
    - **PQ（乘积量化）**：压缩向量以节省内存，常与IVF结合。
- 常见工具：FAISS、Milvus、Qdrant、Weaviate、pgvector、Elasticsearch/OpenSearch等。

Q6：***什么是混合检索（Hybrid Search）？为什么需要它？***

- 把**稀疏检索（关键词，如BM25）**与**稠密检索（向量）**结合。
- 原因：
    - 向量检索擅长语义匹配、同义改写，但对**专有名词、编号、代码、罕见词**的精确匹配较弱；
    - BM25擅长精确关键词匹配，但不理解语义。
- 融合方法：
    - **加权求和**（需要归一化分数）；
    - **RRF（Reciprocal Rank Fusion）**：$score(d)=\sum_{i}\frac{1}{k+rank_i(d)}$，只依赖排名，无需分数校准，简单稳健。

Q7：***什么是重排序（Reranking）？为什么它能提升效果？***

- 先用快速的检索器召回较多候选（如Top-50~100），再用更精细的模型对候选重新打分，选出Top-K送入LLM。
- 常用**交叉编码器（cross-encoder）**：把查询和文档**拼接在一起**输入模型，进行完整的交互注意力计算，相关性判断比双塔模型精确得多，但计算量大，只适合在少量候选上使用。
- 也可以用LLM做重排序（listwise/pointwise）。
- 本质是**“召回-精排”两阶段**：第一阶段追求召回率，第二阶段追求精确率。

Q8：***有哪些查询端的优化方法？***

- **查询改写**：把口语化、含指代的多轮问题改写成独立完整的检索query；
- **多查询（multi-query）**：生成多个不同表述的查询分别检索后合并；
- **查询分解**：把复杂问题拆成多个子问题分别检索；
- **HyDE**：先让LLM生成一个假设答案，用它的embedding去检索；
- **元数据过滤**：按时间、来源、权限等字段过滤；
- **Step-back提问**：先检索更抽象的背景知识。

Q9：***如何评估RAG系统？***

- **检索层**：Recall@K、Precision@K、MRR、nDCG，衡量相关文档是否被检索到、排名是否靠前；
- **生成层**：
    - **忠实度（faithfulness/groundedness）**：回答是否有检索内容支持，有无幻觉；
    - **答案相关性**：是否回答了问题；
    - **正确性**：与参考答案对比；
    - **引用准确性**：引用是否确实支持对应论断；
- 方法：构建带标注的问答评估集，结合人工评估与LLM-as-judge；Ragas等框架提供了常用指标的实现。
- 要**分别诊断**是检索失败还是生成失败。

Q10：***什么是Agentic RAG？与传统RAG有何区别？***

- **传统RAG**：固定流水线，每次查询都检索一次，检索结果直接用于生成。
- **Agentic RAG**：把检索作为Agent的**工具**，由模型决定：
    - 是否需要检索、检索什么、用哪个数据源（向量库、SQL、网页搜索、代码库grep等）；
    - 根据结果判断信息是否足够，不够则**改写查询、多跳检索**；
    - 对检索结果进行验证和综合。
- 优点：能处理多跳、复杂问题，适应性强；缺点：延迟和成本更高，行为更难预测。
- 在代码等场景中，Agent常用**grep/文件浏览等“即时检索”**替代或补充预先构建的向量索引。

Q11：***长上下文模型出现后，RAG还有必要吗？***

- 仍然有必要，但二者是**互补**关系：
    - 知识库规模往往远超上下文窗口；
    - 把大量内容塞进上下文**成本高、延迟大**；
    - 上下文过长时模型对中间信息的利用能力会下降（**“Lost in the Middle”**现象），噪声也会干扰推理；
    - RAG便于做**权限控制、实时更新和引用溯源**。
- 长上下文降低了对检索精度的要求：可以检索更多、更大的块，让模型自己筛选。

Q12：***Agent的长期记忆应如何设计？***

- **写入**：决定记什么——用户偏好、关键事实、任务结论、经验教训；可以由Agent通过“记忆工具”主动写入，也可以在会话结束后由后台流程**抽取和总结**。
- **存储**：向量库（语义检索）、键值/关系数据库（结构化事实）、知识图谱（实体关系）、文件（如Markdown笔记）。
- **检索**：按相关性、时间新近度、重要性综合打分，取回放入上下文。
- **更新与遗忘**：处理冲突和过时信息（新事实覆盖旧事实）、去重、合并，设置过期策略。
- **隐私与安全**：用户可查看和删除记忆，防止通过记忆注入恶意指令、防止跨用户泄露。

Q13：***什么是上下文窗口管理？有哪些常用策略？***

- 随着Agent循环进行，对话历史和工具结果不断累积，最终会超出上下文窗口或导致性能下降，需要主动管理。
- 常用策略：
    - **滑动窗口**：只保留最近N轮，简单但会丢失早期信息；
    - **摘要/压缩（compaction）**：当上下文接近上限时，让模型把历史总结成精简摘要，用摘要开启新的上下文继续工作；
    - **工具结果清理**：删除或替换已经处理过的旧工具结果；
    - **外部记忆/笔记**：Agent把进度、计划、关键发现写入文件（如`NOTES.md`、待办列表），需要时再读回；
    - **子Agent**：把需要大量探索的子任务交给子Agent，只返回精炼结果；
    - **按需检索**：只保存引用（文件路径、URL），需要时再加载内容。

Q14：***上下文压缩（Compaction）时应保留哪些信息？有什么风险？***

- 应保留：用户的原始目标和约束、已做出的关键决策及其原因、当前进度和下一步计划、未解决的问题/错误、重要的文件路径或标识符。
- 可丢弃：冗余的工具原始输出、已经解决的中间尝试、重复内容。
- 风险：
    - **信息丢失**：摘要遗漏了后续才发现重要的细节；
    - 过度压缩导致模型重复已做过的工作；
- 缓解：保留可回查的原始记录（日志/文件），压缩提示中明确列出必须保留的内容，并通过评估调整压缩策略。

Q15：***RAG中常见的问题有哪些？如何解决？***

- **检索不到**：改进chunking、使用混合检索、查询改写、微调embedding；
- **检索到但排名靠后**：加入reranker；
- **检索到但模型不用/用错**：优化提示，要求基于上下文回答并引用；减少噪声块；
- **文档解析质量差**：表格、图片、多栏PDF需要专门的解析（版面分析、OCR、多模态模型）；
- **知识冲突/过时**：加入时间元数据，优先返回最新版本；
- **权限泄露**：在检索阶段按用户权限过滤（文档级ACL）。

Q16：***什么是GraphRAG？适用于什么场景？***

- GraphRAG先用LLM从文档中**抽取实体和关系构建知识图谱**，并对图做社区检测与分层摘要，检索时结合图结构和摘要。
- 适用场景：需要**全局性、跨文档的综合问题**（如“这些报告的主要主题是什么”）、多跳关系推理。
- 缺点：构建图谱成本高，更新复杂；对于简单的事实查找，传统向量RAG通常已足够。
