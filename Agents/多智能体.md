# 多智能体

Q1：***什么是多智能体系统（Multi-Agent System）？***

- 由**多个LLM Agent协作**完成任务的系统，每个Agent可以有不同的角色、提示、工具、模型甚至权限。
- Agent之间通过消息传递、共享状态或工具调用进行通信与协作。
- 动机：任务分工与专业化、并行加速、突破单个上下文窗口的限制、隔离职责与权限。

Q2：***常见的多Agent架构有哪些？***

- **编排者-工作者（Orchestrator-Worker）**：一个主Agent负责规划和拆分任务，把子任务分派给多个工作者Agent（常并行执行），最后汇总结果；
- **监督者（Supervisor）/层级式**：监督者Agent根据当前状态决定把控制权交给哪个专业Agent，可多层嵌套；
- **交接/路由（Handoff）**：Agent之间直接把对话控制权移交给更合适的Agent（如客服中从分诊Agent交给退款Agent）；
- **顺序流水线**：多个Agent按固定顺序处理（如研究员 → 写手 → 审稿人）；
- **辩论（Debate）/多角色讨论**：多个Agent就同一问题给出观点并相互批判，最终由裁判或共识得出结论；
- **去中心化/网络式（Swarm）**：Agent之间点对点通信，没有中心控制者。

Q3：***Orchestrator-Worker模式是如何工作的？优缺点是什么？***

- 流程：
    1. 编排者分析任务，制定计划并拆分为若干子任务；
    2. 为每个子任务撰写清晰的指令（目标、输出格式、可用工具、边界），启动工作者Agent；
    3. 工作者在**各自独立的上下文**中执行，返回精炼的结果；
    4. 编排者整合结果，必要时启动新一轮子任务，最后输出答案。
- 优点：易于并行、上下文隔离、编排者保持全局视图；
- 缺点：编排者是瓶颈和单点故障；子任务描述不清会导致工作者重复工作或偏题；token消耗大。

Q4：***什么是子Agent（Subagent）？为什么说它能实现“上下文隔离”？***

- 子Agent是由主Agent启动的、拥有**独立上下文窗口**的Agent，用来完成一个边界清晰的子任务（如“搜索代码库中所有调用X的地方”）。
- 上下文隔离：子Agent在探索过程中可能读取大量文件、网页、工具输出，这些**中间内容只存在于子Agent的上下文中**；主Agent只收到最终的精炼摘要。
- 好处：
    - 主Agent的上下文保持干净，避免被无关细节污染（缓解上下文腐化）；
    - 可以并行运行多个子Agent；
    - 可为子Agent配置不同的工具、权限或更便宜的模型。
- 代价：主Agent看不到细节，若摘要遗漏信息会影响后续决策；启动子Agent本身也有开销。

Q5：***多Agent之间如何通信？***

- **消息传递**：Agent以自然语言或结构化消息（JSON）相互发送请求和结果；
- **共享状态/黑板（Blackboard）**：所有Agent读写同一个状态对象或共享存储；
- **共享文件系统**：子Agent把详细结果写到文件，只返回文件路径，避免通过上下文“传话”造成信息损失；
- **工具化调用**：把一个Agent包装成另一个Agent可以调用的工具（agent-as-tool）；
- **标准协议**：如A2A（Agent2Agent）等协议，用于不同厂商/框架的Agent之间互相发现能力和协作；MCP则主要用于Agent与工具/数据之间的连接。

Q6：***多Agent系统的成本和延迟有什么特点？***

- **成本**：每个Agent都有自己的系统提示、工具定义和上下文，多Agent系统的**token消耗通常显著高于单Agent**（可能是数倍甚至更多）。
- **延迟**：
    - 并行执行子任务可以**降低总耗时**（广度型任务）；
    - 但串行的多轮协调、交接、汇总会**增加延迟**。
- 因此多Agent适合**价值高、可并行、信息量大**的任务；对于简单或强依赖、需要紧密共享上下文的任务（如大多数编码任务的同一处修改），单Agent往往更划算。

Q7：***什么时候应该使用多Agent，什么时候不应该？***

- 适合：
    - **广度优先、可并行**的任务（如同时调研多个独立方向）；
    - 信息量超出单个上下文窗口；
    - 需要不同专业工具/权限的明确分工；
    - 需要独立视角进行审查（如生成者与审核者分离）。
- 不适合：
    - 子任务之间**依赖强、需要共享大量上下文**；
    - 需要高度一致性的产出（多个Agent各自决策容易产生冲突，比如多个Agent并行写同一份代码风格不一致）；
    - 成本或延迟敏感的简单任务。

Q8：***多Agent系统有哪些典型的失败模式？***

- **任务描述不清**：编排者给出的指令模糊，导致工作者重复工作、遗漏或理解偏差；
- **信息在传递中丢失**：“传话游戏”效应，摘要丢掉了关键细节；
- **决策冲突**：并行Agent做出相互矛盾的隐式假设，合并结果时不一致；
- **过度生成Agent**：对简单问题也启动大量子Agent，浪费资源；
- **循环与死锁**：Agent之间互相交接或互相等待；
- **角色混淆**：Agent不遵守自己的角色边界；
- **验证缺失**：没有Agent对最终结果负责，错误被层层传递；
- **错误级联**：一个Agent的错误输出成为其他Agent的输入。

Q9：***如何提升多Agent系统的可靠性？***

- 编排者给子Agent的指令要包含：**明确目标、输出格式、可用工具和信息源、任务边界、何时停止**；
- 根据任务复杂度设定**投入规模**（简单问题少量调用，复杂问题更多子Agent）；
- 使用**结构化输出**和共享文件减少信息损失；
- 增加专门的**验证/审核Agent**或基于测试的检查；
- 完整的**追踪（tracing）**，记录每个Agent的输入、输出、工具调用；
- 对长时间运行的系统支持**检查点和断点续跑**，避免失败后从头开始；
- 通过评估迭代编排者的提示（很多问题源于编排者的委派方式）。

Q10：***什么是多Agent辩论（Multi-Agent Debate）？有什么作用？***

- 多个Agent（可以是同一个模型的不同实例或不同模型）各自给出答案，然后**阅读彼此的回答并反驳或修正**，经过若干轮后由裁判Agent或投票得出最终答案。
- 作用：在部分推理和事实性任务上可以提升准确性，减少单个模型的偏差。
- 局限：
    - 成本高；
    - 同一模型的多个实例可能**共享相同的偏差**，容易趋同于错误答案（从众效应）；
    - 有研究指出，在相同计算预算下，其收益不一定优于自洽性投票等更简单的方法。

Q11：***Agent之间“交接（Handoff）”应如何设计？***

- 交接是把**对话控制权**从一个Agent转移给另一个Agent，常用于客服等多领域场景。
- 设计要点：
    - 把交接实现为一个工具（如`transfer_to_refund_agent`），由模型决定何时调用；
    - 交接时传递**必要的上下文**（用户信息、已收集的信息、问题摘要），避免让用户重复描述；
    - 定义清晰的职责边界，防止来回踢皮球；
    - 提供交接回主Agent或转人工的路径。

Q12：***多Agent系统中如何管理共享状态？***

- 明确**状态的单一事实来源**（如数据库、共享文件、编排者维护的状态对象）；
- 对并发写入加锁或采用只追加（append-only）日志，避免竞态；
- 每个Agent只读取完成其任务所需的状态，避免上下文膨胀；
- 对状态变更进行版本化和记录，便于回溯与调试。

Q13：***如何评估多Agent系统？***

- **端到端结果**：任务成功率、答案质量（可用LLM-as-judge按评分标准评估）；
- **过程指标**：子Agent数量、工具调用次数、token消耗、耗时、重复工作比例；
- **轨迹分析**：查看委派是否合理、信息是否在传递中丢失；
- 由于多Agent系统**非确定性强**，同一输入运行多次的路径可能不同，因此应关注结果是否达成目标，而不是要求固定的执行步骤；
- 与单Agent基线对比，确认额外成本带来了相应收益。

Q14：***多Agent系统中如何处理权限与安全？***

- **最小权限原则**：每个Agent只拥有完成其职责所需的工具和权限；
- 处理不可信输入的Agent（如浏览网页、读取邮件）与拥有高权限操作的Agent**隔离**，二者之间只传递经过约束的结构化数据；
- 防止提示注入在Agent之间**传播**：来自其他Agent的消息也应视为不完全可信；
- 对高风险动作保留人工审批。
