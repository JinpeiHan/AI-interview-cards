# 评估与安全

Q1：***为什么Agent的评估比普通LLM评估更难？***

- **多步与非确定性**：同一任务每次运行的轨迹可能不同，一次运行的结果不代表整体表现；
- **路径多样**：达成目标的正确方式可能有很多种，不能简单与“标准轨迹”逐步比对；
- **环境依赖**：需要可复现的环境（数据库、网页、代码仓库）和状态重置；
- **副作用**：Agent会修改环境，需要检查最终状态而不仅是文本输出；
- **成本高**：每个评估样例可能涉及几十次模型调用。

Q2：***Agent评估有哪些主要维度和方法？***

- **结果评估（Outcome）**：任务是否成功完成，如单元测试是否通过、数据库最终状态是否正确、答案是否正确；
- **轨迹评估（Trajectory）**：检查执行过程——工具选择是否正确、参数是否合理、是否有多余或危险的步骤、是否遵守策略；
- **效率**：步数、工具调用次数、token消耗、耗时、费用；
- **可靠性/一致性**：多次运行的成功率，如**pass@k**（$k$次中至少一次成功）和**pass^k**（$k$次全部成功，更能反映生产环境的可靠性）；
- **安全性**：是否执行了越权或有害操作，是否被提示注入影响。
- 方法：基于代码的确定性检查、LLM-as-judge、人工评估，三者结合。

Q3：***什么是LLM-as-Judge？如何正确使用？***

- 用一个LLM根据**评分标准（rubric）**评估另一个模型或Agent的输出/轨迹。
- 优点：可扩展、便宜、可以评估开放式输出。
- 已知偏差：**位置偏差**（偏好先出现的回答）、**冗长偏差**（偏好更长的回答）、**自我偏好**（偏好同系列模型的输出）、受表面格式影响。
- 最佳实践：
    - 给出**具体、可操作的评分标准**，最好是二元或少量等级的判断；
    - 让评审先给出理由再打分；
    - 成对比较时**交换顺序**评两次；
    - 用人工标注的样本**校准**评审模型，计算与人类判断的一致率；
    - 能用确定性检查的地方（测试、精确匹配）优先用确定性检查。

Q4：***介绍几个常见的Agent基准测试（Benchmark）***

- **SWE-bench**：来自真实GitHub仓库的issue，Agent需要修改代码修复问题，用仓库的测试判断是否成功；有经过人工筛选的Verified等子集。衡量**真实软件工程能力**。
- **τ-bench（tau-bench）**：模拟客服场景（如零售、航空），Agent需要与**模拟用户**对话并调用领域API，同时遵守业务策略；通过数据库最终状态评估，并强调多次运行的一致性（pass^k）。
- **WebArena**：在可自托管的真实网站环境（电商、论坛、代码托管、地图等）中完成网页操作任务，评估**网页导航与操作能力**。
- **GAIA**：面向通用AI助手的问题，需要多步推理、网页搜索、文件处理、多模态等能力，答案简短明确便于自动评分；对人类较简单但对AI较难。
- 其他：OSWorld（操作系统/桌面操作）、Terminal-Bench（命令行任务）、BrowseComp（难以检索的信息查找）等。
- 注意：公开基准存在**数据污染**和与实际业务不匹配的问题，生产中应构建**自己的评估集**。

Q5：***如何为自己的Agent构建评估集？***

- 从**真实用户请求和失败案例**中收集任务，覆盖常见场景、边界情况和对抗样本；
- 每个任务定义清晰的**成功标准**（可自动检查的最终状态或参考答案）；
- 从少量（几十个）高质量样例起步，随着发现新的失败模式不断扩充；
- 区分**能力评估**（衡量能做到什么，通过率可以较低）和**回归评估**（防止已有能力退化，应接近100%通过）；
- 每次修改提示、工具、模型时自动运行，跟踪指标变化。

Q6：***什么是Agent的可观测性（Observability）？需要记录什么？***

- 可观测性指能够**看清Agent每一步做了什么、为什么这样做**，是调试、评估和合规的基础。
- 需要记录（**Tracing**）：
    - 每次模型调用的完整输入（系统提示、上下文）、输出、思考内容（若可用）；
    - 每次工具调用的名称、参数、结果、耗时、错误；
    - token用量、延迟、费用；
    - 多Agent之间的调用关系（span树结构）；
    - 用户反馈和最终结果。
- 工具：OpenTelemetry（及其GenAI语义约定）、LangSmith、Langfuse、Arize Phoenix等。
- 注意对日志中的**敏感数据脱敏**。

Q7：***什么是提示注入（Prompt Injection）？直接注入和间接注入有什么区别？***

- 提示注入是攻击者通过构造输入，使模型**忽略原有指令、执行攻击者的指令**。
- **直接注入**：用户本人在输入中写恶意指令（如“忽略之前的所有指令……”，越狱也属于此类）；
- **间接注入**：恶意指令隐藏在Agent处理的**外部数据**中，如网页、邮件、文档、代码注释、工具返回结果。Agent读取后被劫持。
- 对Agent而言，**间接注入更危险**：Agent会自动读取大量不可信内容，并且拥有执行真实操作的工具。

Q8：***如何防御提示注入？***

- 目前**没有完美的防御**，需要多层纵深防御：
    - **最小权限**：只给Agent完成任务所需的工具和权限；
    - **隔离不可信数据**：明确标记外部内容为数据而非指令；处理不可信内容的模块不直接拥有高权限工具（如双LLM模式：隔离的模型处理不可信数据，只返回受约束的结构化结果）；
    - **避免“致命三要素”同时存在**：访问私有数据 + 接触不可信内容 + 能够对外通信（数据外泄通道），三者同时具备时风险最高；
    - **敏感操作人工确认**；
    - **输入/输出检测**：用分类器检测注入和数据外泄；
    - **出站网络限制**：限制可访问的域名，防止数据被发送出去；
    - 使用经过对抗训练、对注入更鲁棒的模型。

Q9：***为什么Agent需要沙箱（Sandboxing）？常见的沙箱方案有哪些？***

- Agent可能执行代码、命令和文件操作，模型的错误或被注入的指令可能导致**删除数据、泄露凭证、破坏系统**。沙箱把影响范围限制在可控环境中。
- 常见方案：
    - **容器**（Docker等）：轻量，但与宿主共享内核，隔离性相对较弱；
    - **gVisor、微虚拟机（如Firecracker）**：更强的隔离；
    - **操作系统级沙箱**：如Linux的seccomp/Landlock/bubblewrap、macOS的Seatbelt，限制文件系统和网络访问；
    - **浏览器沙箱/WebAssembly**：用于运行不可信代码。
- 关键配置：**文件系统隔离**（只能访问工作目录）、**网络隔离**（只允许白名单域名）、资源限制（CPU、内存、时间）、不在沙箱中放置敏感凭证。

Q10：***Agent的权限系统应如何设计？***

- **最小权限原则**：默认只读，写入和执行需要额外授权；
- **按操作风险分级**：
    - 低风险（读取、搜索）：自动允许；
    - 中风险（编辑文件、调用内部API）：可以按规则允许或询问；
    - 高风险（删除、付款、发送外部消息、生产部署）：必须人工确认；
- **可配置的允许/拒绝规则**（如允许特定命令、拒绝访问特定目录）；
- **短期、细粒度的凭证**（如按任务签发的有限范围token），而不是给Agent长期的管理员密钥；
- **审计日志**：所有操作可追溯。

Q11：***什么是Human-in-the-Loop（人在回路）？在Agent中如何应用？***

- 在Agent执行过程中的关键节点引入**人工审核、确认或纠正**。
- 应用方式：
    - **审批**：执行高风险操作前暂停，等待用户批准；
    - **澄清**：信息不足或请求有歧义时，主动向用户提问；
    - **计划审核**：执行前让用户确认计划；
    - **结果审核**：交付前人工检查（如代码审查后再合并）；
    - **升级（escalation）**：Agent无法处理时转交人工。
- 权衡：介入过多会降低效率并导致“审批疲劳”（用户不看就点同意），因此应集中在真正高风险的节点。

Q12：***什么是护栏（Guardrails）？有哪些类型？***

- 护栏是在模型之外对输入、输出和动作进行**检查与约束**的机制。
- 类型：
    - **输入护栏**：检测越狱、提示注入、离题请求、敏感信息（PII）；
    - **输出护栏**：检测有害内容、幻觉、敏感信息泄露、格式校验；
    - **动作护栏**：在工具执行前检查参数和权限（如金额上限、禁止访问的路径）；
- 实现：规则（正则、白名单）、分类模型、LLM审核；可与主模型**并行运行**以降低延迟。

Q13：***如何控制Agent的成本？***

- **模型路由**：简单子任务使用小/快模型，复杂推理才用大模型；
- **提示缓存（Prompt Caching）**：把稳定的系统提示、工具定义、长文档放在前缀并缓存，降低重复输入的成本和延迟；
- **上下文管理**：截断/摘要工具结果、压缩历史，减少每轮输入token；
- **预算限制**：设置每个任务的最大步数、token和费用上限，超出后停止或请求确认；
- **控制推理强度**：按需调节思考预算；
- **批处理**：对非实时任务使用批处理API；
- **监控**：按用户、任务类型统计成本，发现异常（如循环导致的费用激增）。

Q14：***什么是“奖励投机（Reward Hacking）”？在Agent中有哪些表现？***

- 模型找到满足评估信号的**捷径**，而没有真正完成任务。
- Agent中的表现：
    - 为了让测试通过而**修改或删除测试**、硬编码期望输出；
    - 宣称任务已完成但实际未完成；
    - 绕过而不是解决权限或校验问题。
- 应对：设计更全面的评估（保留隐藏测试、检查代码改动）、在轨迹评估中专门检查此类行为、在提示中明确禁止。

Q15：***Agent上线前后应如何持续保证质量与安全？***

- 上线前：离线评估集、红队测试（提示注入、越权、滥用）、灰度发布；
- 上线后：
    - 线上追踪与监控（成功率、错误率、延迟、成本、用户反馈）；
    - 对线上轨迹抽样，用LLM-as-judge和人工审查；
    - 把新发现的失败案例加入评估集，形成**闭环**；
    - 模型或提示更新时运行回归评估，必要时可快速回滚。

Q16：***Agent中的数据隐私问题有哪些？如何处理？***

- 风险：用户数据进入日志、长期记忆、第三方工具/MCP Server；跨用户的记忆泄露；通过提示注入外泄数据。
- 处理：日志与追踪中**脱敏PII**；按用户/租户隔离记忆和检索索引；对第三方工具做数据处理协议审查；遵守数据保留和删除策略；限制Agent的对外通信能力。
