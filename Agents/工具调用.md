# 工具调用

Q1：***什么是Function Calling / Tool Calling？它是如何工作的？***

- Tool Calling是让LLM**以结构化格式（通常是JSON）请求调用外部函数**的能力。
- 流程：
    1. 开发者在请求中提供工具定义（名称、描述、参数的JSON Schema）；
    2. 模型判断是否需要工具，若需要则输出一个**工具调用块**（工具名 + 参数）；
    3. **应用程序**解析并执行该函数，把结果作为**工具结果消息**回传给模型；
    4. 模型基于结果继续推理，可能再次调用工具或给出最终回答。
- 关键：**模型只产生“调用意图”，不执行代码**；执行、权限、安全都由应用负责。

Q2：***模型是如何学会调用工具的？***

- 主要通过**后训练**：在包含工具定义、工具调用和工具结果的对话数据上做监督微调（SFT），再通过强化学习（RL）在真实或模拟环境中优化多步工具使用。
- 推理时，工具定义被注入到系统提示/特殊模板中，模型输出带有特殊标记的结构化调用，由服务端解析成API中的tool call对象。
- 部分API支持**受约束解码（constrained decoding）**，保证输出的参数严格符合JSON Schema。

Q3：***一个好的工具Schema应该如何设计？***

- **名称**：清晰、动词开头、带命名空间，如`github_create_issue`，避免歧义；
- **描述**：说明工具做什么、**什么时候该用/不该用**、参数含义、返回内容、限制条件，必要时附示例；
- **参数**：
    - 使用明确的类型、`enum`、`required`字段，减少自由文本；
    - 参数名自解释（`user_id`而不是`id`）；
    - 避免让模型做复杂格式转换（如要求它手写转义的长字符串）；
- **粒度**：围绕**用户意图/任务**设计工具，而不是简单地把每个底层API端点一一包装；能合并的高频组合操作可以合并成一个工具；
- **返回值**：返回精简、高信号、对模型有意义的信息（如名称而非内部UUID），支持分页、过滤和截断。

Q4：***什么是MCP（Model Context Protocol）？解决了什么问题？***

- MCP是Anthropic于2024年底提出的**开放协议**，用于标准化LLM应用与外部工具、数据源之间的连接，常被比喻为“AI应用的USB-C接口”。
- 解决的问题：没有统一标准时，$M$个应用接入$N$个工具需要$M \times N$个定制集成；有了MCP，每个应用实现一次客户端、每个工具实现一次服务端，集成成本降为$M + N$。
- 目前已被主流模型厂商、IDE和Agent框架广泛支持。

Q5：***MCP的架构和核心概念是什么？***

- **架构**：
    - **Host（宿主）**：用户使用的AI应用，如聊天客户端、IDE、Agent；
    - **Client（客户端）**：Host内部与某个Server保持一对一连接的组件；
    - **Server（服务端）**：暴露能力的程序，如GitHub、数据库、文件系统的MCP Server。
- **通信**：基于**JSON-RPC 2.0**；传输方式包括本地的**stdio**和远程的**Streamable HTTP**（远程场景通常配合OAuth授权）。
- **Server提供的原语**：
    - **Tools**：模型可调用的函数（由模型控制）；
    - **Resources**：可读取的数据/上下文，如文件内容（由应用控制）；
    - **Prompts**：可复用的提示模板（由用户控制）。
- **Client提供的能力**：如**Sampling**（让Server请求Host的模型生成内容）、**Elicitation**（向用户请求补充信息）、Roots（告知可访问的范围）。

Q6：***MCP和普通Function Calling有什么关系？***

- Function Calling是**模型层面**的能力：模型如何输出结构化的工具调用；
- MCP是**应用集成层面**的协议：工具如何被发现、描述、调用和传输。
- 在运行时，Host通过MCP获取Server的工具列表（`tools/list`），把它们转换成模型API的工具定义；模型发出tool call后，Host再通过MCP（`tools/call`）转发给Server执行。**二者是互补关系**。

Q7：***使用MCP有哪些安全风险？***

- **工具投毒（tool poisoning）**：恶意Server在工具描述中嵌入隐藏指令，影响模型行为；
- **提示注入**：工具返回的内容（网页、邮件、issue）里包含恶意指令；
- **权限过大**：Server持有高权限凭证，被诱导执行破坏性操作或泄露数据；
- **“地毯式”更新（rug pull）**：Server在用户批准后更改工具定义；
- **数据外泄**：组合使用读私有数据的工具和能对外发送的工具。
- 防护：只使用可信来源的Server、最小权限、敏感操作需人工确认、工具定义变更要提醒、对输出做隔离与审查。

Q8：***什么是Structured Output（结构化输出）？有哪些实现方式？***

- 让模型输出**严格符合预定义格式**（通常是JSON Schema）的结果，便于程序解析。
- 实现方式：
    - **提示约束**：在提示中给出格式和示例，最简单但不保证正确；
    - **JSON mode**：保证输出是合法JSON，但不保证符合具体Schema；
    - **Schema约束解码（strict mode）**：在解码时用语法/有限状态机屏蔽不合法的token，**保证符合Schema**；
    - **借用工具调用**：定义一个“提交结果”工具，让模型通过调用它输出结构化数据；
    - **后处理校验**：用Pydantic等校验，失败则把错误信息反馈给模型重试。
- 注意：强约束可能略微影响推理质量，可以让模型先推理，再输出结构化结果。

Q9：***工具调用出错时应该如何处理？***

- **区分错误类型**：
    - 参数错误/校验失败：把**清晰、可操作的错误信息**作为工具结果返回给模型（如“参数date必须为YYYY-MM-DD格式”），让模型自行修正；
    - 临时性错误（超时、限流、5xx）：在运行时层面做**指数退避重试**，不必让模型感知；
    - 永久性错误（无权限、资源不存在）：明确告知模型，让其换方案或向用户求助。
- 将错误标记为错误（如`is_error`），而不是让运行时直接崩溃；
- 设置**最大重试次数**，避免模型反复用相同参数重试；
- 对有副作用的操作，重试时需保证**幂等性**（如使用幂等键），避免重复下单、重复发邮件。

Q10：***什么是并行工具调用（Parallel Tool Calls）？有什么注意事项？***

- 模型在一次回复中输出**多个相互独立的工具调用**，运行时可并发执行，再把所有结果一起返回，从而**减少往返次数和延迟**。
- 典型场景：同时查询多个城市天气、同时读取多个文件、同时发起多个搜索。
- 注意事项：
    - 只有**互不依赖**的调用才能并行；有依赖的必须串行；
    - 每个结果必须通过**tool_call_id**与对应调用匹配；
    - 有副作用的写操作并行时要考虑竞态和顺序问题，必要时可在API中关闭并行调用；
    - 可在提示中鼓励模型对独立操作进行并行调用。

Q11：***当工具数量非常多（几十到上千个）时，如何让模型正确选择工具？***

- 问题：工具定义占用大量上下文token，且相似工具过多会降低选择准确率。
- 方法：
    - **工具检索/动态加载**：根据当前任务用向量检索或关键词匹配选出相关工具，只把它们放入上下文（如提供一个“搜索工具”的元工具，按需加载完整定义）；
    - **分层路由**：先选类别/子Agent，再在类别内部选工具；
    - **合并与精简**：合并功能重叠的工具，删除很少使用的工具；
    - **命名空间**：用前缀区分不同服务，如`slack_`、`jira_`；
    - **代码执行替代**：让Agent写代码调用API（把工具暴露为代码库），而不是把所有工具定义都放进上下文。
- 通过评估集持续测量工具选择准确率。

Q12：***`tool_choice`参数有什么作用？***

- 控制模型是否/如何使用工具，常见取值：
    - **auto**：模型自行决定是否调用工具（默认）；
    - **required/any**：必须调用至少一个工具；
    - **指定工具**：强制调用某个特定工具（常用于结构化抽取）；
    - **none**：禁止调用工具。
- 注意：在部分支持扩展思考的模型中，强制调用工具可能与思考模式不兼容，需查阅具体API文档。

Q13：***工具返回的结果太长怎么办？***

- 在工具层面**截断、分页、过滤**，并告知模型结果已被截断以及如何获取更多（如提供`offset`参数）；
- 提供“响应详细程度”参数（如`concise`/`detailed`），让模型按需选择；
- 对大结果先写入文件/存储，只返回摘要和引用路径，由模型按需读取；
- 用小模型对结果做摘要后再返回；
- 清理历史中已经不再需要的旧工具结果（tool result clearing）。

Q14：***如何评估和改进工具的设计？***

- 构建**贴近真实使用的评估任务**，统计任务成功率、工具调用次数、错误率、token消耗；
- 阅读Agent的**完整轨迹**，观察模型在哪里误解了工具（选错工具、参数错误、多余调用）；
- 根据观察修改工具描述、参数和返回格式，迭代对比；
- 甚至可以让模型分析失败轨迹并建议工具描述的改进。

Q15：***工具调用中的“人工确认（human approval）”应如何设计？***

- 按风险分级：只读操作自动执行；**不可逆或高影响操作**（删除、转账、发送邮件、部署）需用户确认；
- 确认界面应展示**具体参数**和影响，而不是笼统地“是否允许”；
- 支持“本次允许/始终允许此类操作”等权限策略，在安全性和用户体验之间平衡；
- 被拒绝时，把拒绝原因作为工具结果返回给模型，让其调整方案。

Q16：***Tool Calling和Code Execution（让模型写代码执行）各有什么优缺点？***

- **Tool Calling**：
    - 优点：接口明确、易于做权限和校验、安全性好；
    - 缺点：每个调用都要一次模型往返，复杂的数据处理需要多次调用，中间结果都要经过上下文。
- **Code Execution（代码即动作）**：
    - 优点：表达能力强，可以在一段代码中组合多次调用、循环、过滤，**中间数据留在执行环境中，节省上下文token**；
    - 缺点：需要安全的**沙箱**，行为更难审计和限制。
- 实践中常结合使用：常规操作用工具，复杂数据处理交给代码执行环境。
