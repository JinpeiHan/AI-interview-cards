# Agent系统设计

Q1：***回答Agent系统设计题的一般框架是什么？***

1. **明确需求**：用户是谁、要完成什么任务、成功标准、规模（QPS、并发）、延迟和成本要求、风险等级；
2. **判断是否真的需要Agent**：能用Workflow解决的部分尽量用Workflow；
3. **核心架构**：模型选择、工具与数据源、上下文与记忆、单Agent还是多Agent；
4. **可靠性与安全**：护栏、权限、沙箱、人在回路、错误处理与降级；
5. **性能与成本**：缓存、流式输出、模型路由、并行；
6. **评估与可观测性**：离线评估集、线上监控、反馈闭环。

Q2：***设计一个电商客服Agent***

- **需求**：回答订单、物流、退换货、商品问题；可执行查询订单、发起退款等操作；7×24小时、低延迟、遵守公司政策。
- **架构**：
    - **路由/分诊**：先识别意图（小模型或分类器），简单FAQ走RAG直接回答，复杂事务交给带工具的Agent，也可以按领域交接给不同的专业Agent；
    - **工具**：`get_order`、`track_shipment`、`create_return`、`issue_refund`、`search_kb`、`escalate_to_human`；
    - **知识**：政策文档和FAQ通过RAG检索，确保回答基于最新政策；
    - **用户上下文**：身份验证后加载用户信息和近期订单，工具只能访问**当前用户**的数据。
- **护栏与安全**：
    - 退款金额超过阈值或不符合政策时需人工审批；
    - 输入检测越狱/注入，输出检测承诺（如“给你全额赔偿”）是否超出政策；
    - 情绪激动、多次未解决或用户要求时**转人工**，并附上对话摘要。
- **评估**：用模拟用户（类似τ-bench）+ 真实工单回放评估，关注解决率、政策遵守率、转人工率、用户满意度、多次运行的一致性。

Q3：***设计一个代码Agent（Coding Agent）***

- **需求**：在代码仓库中理解需求、修改代码、运行测试、提交修改，可在IDE/终端/CI中运行。
- **核心工具**：读文件、搜索（grep/glob）、编辑文件（基于精确字符串替换或diff）、执行shell命令（运行测试、构建）、版本控制操作。
- **上下文策略**：
    - 不预先把整个仓库放入上下文，而是让Agent通过搜索**按需探索**；
    - 项目级说明文件（如构建命令、代码规范）在启动时加载；
    - 长任务中使用待办列表、上下文压缩，或派子Agent做大范围代码搜索。
- **验证闭环**：修改后运行测试、lint、类型检查，根据失败结果迭代；这是代码Agent效果好的关键——**有可验证的反馈信号**。
- **安全**：在沙箱/容器中执行命令，限制网络访问；危险命令（如`rm -rf`、`git push --force`、部署）需确认；不暴露生产凭证；所有修改通过git可回滚，最终经人工代码审查合并。
- **评估**：SWE-bench类任务 + 内部真实issue，关注测试通过率、改动是否最小化、是否存在修改测试等投机行为。

Q4：***设计一个深度研究Agent（Deep Research Agent）***

- **需求**：针对复杂问题，搜索大量网页/文档，综合多方来源，输出带引用的长篇报告；可以接受分钟级的耗时。
- **架构（编排者-工作者）**：
    1. **澄清**：必要时先向用户确认研究范围；
    2. **规划**：主Agent把问题分解为多个相对独立的子方向；
    3. **并行调研**：为每个方向启动子Agent，各自进行多轮搜索、阅读、筛选，在独立上下文中工作，只返回精炼的发现和来源；
    4. **综合**：主Agent汇总结果，识别信息缺口，必要时启动新一轮调研；
    5. **撰写与引用**：生成报告，由专门步骤核对每个论断是否有来源支持。
- **关键挑战**：来源可信度判断、信息冲突处理、避免重复搜索、token成本高、网页内容中的**间接提示注入**。
- **工程要点**：把中间结果持久化（便于断点续跑），控制子Agent数量和搜索预算，长任务提供进度反馈。
- **评估**：事实准确性、引用准确性、覆盖面、来源质量，通常用LLM-as-judge配合评分标准，再辅以人工抽检。

Q5：***如何降低Agent的延迟？***

- **流式输出**：尽早向用户展示文本和进度（如“正在查询订单……”），降低感知延迟；
- **并行**：并行工具调用、并行子Agent、护栏检查与主模型并行运行；
- **模型路由**：简单步骤用小模型，减少不必要的推理/思考token；
- **提示缓存**：缓存稳定前缀，显著降低首token延迟（TTFT）；
- **减少往返**：合并常用工具操作，让一次工具调用完成更多事情；把确定性步骤用代码实现而不是交给模型；
- **预取**：提前加载可能需要的数据（如用户画像）；
- **结果缓存**：对相同或语义相似的查询复用结果（需注意时效性和个性化）。

Q6：***什么是提示缓存（Prompt Caching）？在Agent中如何利用？***

- 模型服务端缓存**提示前缀**对应的计算结果（KV cache），后续请求如果具有**完全相同的前缀**，可以直接复用，从而**降低输入成本和首token延迟**。
- Agent天然适合：每一轮循环都会重复发送系统提示、工具定义和之前的对话历史，只在末尾追加新内容。
- 设计要点：
    - 把**稳定内容放在前面**（工具定义 → 系统提示 → 长文档 → 对话历史），变化内容放在最后；
    - 避免在前缀中放入时间戳、随机ID等每次变化的内容；
    - 保持工具列表和顺序稳定，动态增删工具会使缓存失效；
    - 注意缓存有存活时间（TTL），不同厂商的使用方式不同（显式断点或自动缓存）；
    - 上下文压缩会改变前缀，需要权衡压缩频率与缓存命中率。

Q7：***Agent系统中应设计哪些降级（Fallback）策略？***

- **模型层**：主模型超时、限流或故障时，切换到备用模型或其他厂商；
- **工具层**：工具失败时重试，仍失败则告知模型使用替代工具或请求用户帮助；
- **任务层**：Agent无法完成时，返回部分结果并清楚说明未完成部分，或转人工；
- **质量层**：输出未通过校验（格式、护栏）时重新生成，或返回安全的默认回复；
- **成本/预算层**：超出预算时停止并汇报进度，而不是无限运行。
- 所有降级行为都应被记录和监控。

Q8：***在系统设计中，如何设计护栏（Guardrails）体系？***

- **分层设计**：
    - 输入层：身份验证、限流、越狱/注入检测、话题范围检查、PII检测；
    - 模型层：清晰的系统提示和行为规范；
    - 动作层：工具参数校验、权限检查、高风险动作人工审批、沙箱执行；
    - 输出层：有害内容过滤、政策合规检查、事实依据检查、格式校验。
- **权衡**：护栏过严会导致误拒，影响用户体验；可以用便宜的快速模型并行检查，只对高风险场景使用更重的检查。
- 护栏规则同样需要评估集来衡量误报率和漏报率。

Q9：***如何为Agent选择模型？***

- 根据**任务难度、延迟、成本**三者权衡：
    - 编排/规划、复杂推理：能力最强的模型（可开启思考）；
    - 大量简单子任务（分类、摘要、抽取）：小而快的模型；
- 关注工具调用能力、长上下文能力、指令遵循能力，而不仅仅是通用排行榜；
- 在自己的评估集上对比不同模型的**成功率 × 成本 × 延迟**；
- 设计时保留**模型可替换性**（抽象模型接口），方便升级和降级。

Q10：***长时间运行（数小时）的Agent任务需要考虑什么？***

- **状态持久化与检查点**：定期保存进度，崩溃或中断后可以恢复，而不是从头开始；
- **上下文管理**：压缩、外部笔记、子Agent，避免上下文溢出和质量下降；
- **进度可见性**：向用户报告进度，允许中途查看和干预；
- **异步执行**：任务在后台运行，完成后通知用户；
- **预算与超时**：防止失控；
- **环境一致性**：沙箱环境可复现，外部依赖变化时能检测到。

Q11：***如何设计Agent的记忆系统以支持个性化？***

- 区分**会话内记忆**（上下文）与**跨会话记忆**（用户偏好、历史事实）；
- 在会话结束时或通过记忆工具抽取值得记住的信息，存入按用户隔离的存储；
- 新会话开始时检索相关记忆放入上下文，或让Agent按需查询；
- 处理记忆冲突与过期，允许用户查看、修改和删除记忆；
- 防止记忆被注入恶意指令，记忆内容应视为数据而非指令。

Q12：***如何设计Agent的评估与迭代流程？***

- 建立**离线评估集**（真实任务 + 边界情况 + 对抗样本），每次改动自动运行；
- 结合**确定性检查、LLM-as-judge、人工评审**；
- 线上**追踪所有轨迹**，监控成功率、延迟、成本、用户反馈；
- 定期抽样分析失败轨迹，定位问题属于提示、工具、检索还是模型能力；
- 将新失败案例加入评估集，形成“发现问题 → 修复 → 回归测试”的闭环；
- 使用A/B测试或灰度发布验证改动在线上的效果。

Q13：***如何设计一个能操作浏览器/电脑的Agent（Computer Use）？***

- **感知**：截图（视觉模型）与/或可访问性树、DOM结构，两者结合通常更可靠；
- **动作**：点击、输入、滚动、按键，或更高层的浏览器操作（导航、填写表单）；
- **挑战**：步骤多、延迟高、页面动态变化、坐标定位误差、网页中的提示注入；
- **安全**：在隔离的虚拟机/浏览器环境运行，不登录敏感账号或使用专用账号，限制可访问的域名，付款、提交表单等关键操作需人工确认；
- **优化**：有API可用时优先使用API，只有在没有API时才使用GUI操作。

Q14：***Agent系统中的多租户与扩展性问题如何处理？***

- **隔离**：每个租户/用户的数据、记忆、检索索引、沙箱环境相互隔离；
- **限流与配额**：按租户限制请求速率和token用量，防止单个租户耗尽资源；
- **无状态服务 + 外部状态存储**：Agent编排服务尽量无状态，会话状态存储在数据库/缓存中，便于水平扩展；
- **队列与异步**：长任务通过任务队列执行，避免占用请求连接；
- **处理模型API限流**：重试、退避、多区域/多供应商分流。
